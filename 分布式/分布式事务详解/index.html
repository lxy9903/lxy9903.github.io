分布式事务详解

1️⃣ 为什么需要分布式事务？

在单体系统中，一次业务基本只涉及一个数据库，用本地事务就能保证原子性、隔离性、一致性、持久性（ACID）。

但在微服务架构中，一次业务往往跨：

  • 多个服务
  • 多个数据库
  • 甚至多个外部系统（支付、库存、消息中间件）

例如：下订单（Order） → 扣库存（Inventory） → 扣余额（Account）
三个步骤都不在同一个数据库，因此本地事务无法覆盖。

于是我们需要 分布式事务 来保证最终一致性。

2️⃣ 主流分布式事务方案详解

按强一致性 → 最终一致性排序：

⭐️ 方案一：2PC / XA（强一致性 / 同步阻塞）

✔ 原理（两阶段提交）

协调者（TM） 和 参与者（RM）

第一阶段：Prepare
各参与者执行操作，但不提交，写日志，锁资源。

第二阶段：Commit
协调者通知各参与者提交或回滚。

✔ 优点

  • 理论上满足 ACID
  • 强一致性（银行、交易类场景可能使用）

✖ 缺点（致命）

  • 同步阻塞：所有资源在 Prepare 阶段锁定
  • 单点风险：协调者挂了事务不确定
  • 性能差，不适合高并发

✔ 使用场景

  • 银行类、强一致性系统（但现代银行不直接使用 XA，通常是 Saga/补偿）

⭐️ 方案二：TCC（Try / Confirm / Cancel）

业务侵入式最高，但一致性更可控。

✔ 原理

每个服务要实现 3 个接口：

阶段 作用
Try 检查资源并“预留”资源
Confirm 真正执行
Cancel 回滚预留资源

✔ 优点

  • 粒度最细、一致性高
  • 可重试，性能比 XA 高很多

✖ 缺点

  • 强业务侵入：每个服务要写 try/confirm/cancel
  • 接口复杂
  • 开发成本大

✔ 使用场景

  • 强一致性 且 业务可拆 try/confirm/cancel
    例如：支付、机票预定、库存预留

⭐️ 方案三：Saga（补偿事务 / 长事务）

适用于长链路、跨多服务的大事务（旅游、订单、机票预订）

✔ 原理

Saga 是一个有序的本地事务链：

S1 → S2 → S3 …

如果有一个出错，例如 S3，执行补偿事务：

CS2 → CS1

补偿事务必须保证逆向回滚逻辑。

✔ 优点

  • 异步执行、性能高
  • 适用于长事务、跨多服务
  • 不阻塞资源

✖ 缺点

  • 最终一致性（不是强一致性）
  • 补偿逻辑复杂
  • 并不保证整体严格回滚（可能失败 & 重试）

✔ 使用场景

  • 酒店预订
  • 分布式订单（确认/取消链路）
  • 长时间操作（支付轮询、物流）

⭐️ 方案四：Outbox / 本地消息表（最常用 & 简洁）

本地事务 + 异步消息最终一致性
解决 “我操作数据库成功了，但给 MQ 发消息失败了” 的经典问题。

✔ 原理（两步）

  1. 本地事务：写业务数据 + 记录待发送消息（outbox 表）
  2. 后台任务或 CDC 解析 Outbox 表 → 发送到 MQ → 标记成功

关键：DB 操作 & 消息记录在同一个事务里，保证一致性。

✔ 优点

  • 实现简单
  • 高性能
  • 一致性强（最终一致）
  • 无业务侵入，几乎适合所有系统

✖ 缺点

  • 最终一致性，需要后台任务或 Debezium/CDC
  • Outbox 表可能变大要归档

✔ 使用场景（最普遍）

  • 电商订单 → 通知库存
  • 订单支付成功 → 发送到 Kafka
  • 用户注册 → 发送欢迎邮件

⭐️ 方案五：Kafka 幂等消息（保证消息不丢、不重、不乱）

核心两套能力：

✔ ① 幂等生产（Idempotent Producer）

Kafka Producer 设置 enable.idempotence=true

确保生产同一消息多次，只会写入一次。

✔ ② Exactly Once 语义（EOS）

Kafka + 消费端 + DB 事务保证如下逻辑：

  • 事务性 Producer（把写消息 + 提交偏移绑定在一起）
  • Consumer 端用幂等 Key 保证重复消息不会影响下游

✔ 优点

  • 性能非常高
  • 支持 exactly-once（在 Kafka 内部链路）

✖ 缺点

  • 只能保证 “Kafka 内部” 的 exactly-once
  • 落地 MySQL/Redis 等需要额外幂等设计

✔ 使用场景

  • 实时账单 pipeline
  • 用户行为日志
  • 订单状态变更事件流
  • 交易流水流转

3️⃣ 如何选择分布式事务方案？

场景 适合方案
强一致性必须保证（例如银行账户） TCC / 协议化事务
超长链路（酒店、订单、机票） Saga
最普遍的电商、订单、库存、支付 Outbox + MQ
高并发事件流 Kafka 幂等消息
老系统、少变化、要求 ACID XA（一般不推荐）
分布式
