分布式锁详解

一、为什么需要分布式锁？

在单机应用中我们可以用 synchronized 或 ReentrantLock 做并发控制，但在分布式系统下，多台机器、多进程会同时操作同一份资源，这时候就必须用 分布式锁 来保证 互斥、可重入、安全释放。

常见使用场景：

  1. 防止超卖（多个节点同时扣库存）
  2. 防止重复下单、重复支付
  3. 定时任务集群只让一台跑
  4. 幂等控制：同一业务不能同时重复执行
  5. 接口限流的临界区保护

二、分布式锁核心要解决哪些问题？

核心诉求有 6 个：

  1. 互斥性：同一时刻只有一个客户端持有锁
  2. 可重入性（可选）
  3. 死锁问题：持有锁的机器宕机必须正确释放
  4. 锁必须只能被持有者释放
  5. 高可用、高性能
  6. 容错：网络超时 / 分区情况下的一致性

三、 案例：电商系统扣库存

需求： 秒杀时 10 万请求并发扣同一商品库存。
问题： 多机房、多实例部署，每个服务实例都可能同时减少库存 → 需要全局互斥。

方案 2：RedLock（多主节点）

“RedLock 是 Redis 作者提出的多主互斥算法，通过在 5 个 Redis 节点上获取多数派（3 个以上）Lock 才算成功。”

然后继续讲：

优点：

  • 抗 Redis 单点故障
  • 理论上容忍任意一个 Redis 节点宕机

缺点：

  • 工程上效果有限，网络分区导致算法不总是安全
  • 在社区内有争议（Martin Kleppmann 的一致性论文）
  • 需要多个独立 Redis 实例（成本高）

方案 3：Zookeeper 分布式锁（最安全）

实现原理：临时顺序节点 + Watcher

创建节点：

流程：

  1. 每个客户端创建一个 EPHEMERAL_SEQUENTIAL 节点
  2. 谁的序号最小谁获得锁
  3. 其他客户端监听前驱节点
  4. 前驱节点被删除（释放锁 / 会话断开）后，触发 watch → 当前客户端获得锁

优点：

  • 强一致（ZAB 协议）
  • 天然不会死锁（临时节点）
  • 公平锁（排队顺序）
  • 可靠性最高

缺点：

  • 性能比 Redis 较差
  • ZK 不适合做超高 QPS 的锁（更适合任务调度、全局抢占）
