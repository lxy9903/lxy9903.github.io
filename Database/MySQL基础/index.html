MySQL — 基础知识

一、MySQL 整体架构（高层与实现细节）

核心组件

  • 客户端 / 协议层：解析客户端协议、权限校验。
  • 连接管理：连接池/线程管理、认证、SSL。
  • 解析器（Parser）/预处理器（Preprocessor）/优化器（Optimizer）：SQL -> AST -> 重写 -> 查询计划（cost-based）。
  • 执行器（Executor）：按计划执行操作，访问存储引擎接口（Handler API）。
  • 存储引擎层（Storage Engine）：InnoDB、MyISAM、Memory、NDB 等。InnoDB 是常用事务引擎。
  • 日志系统：二进制日志（binlog）、错误日志、慢查询日志、事务日志（Redo/Undo for InnoDB）。
  • 信息 & 监控：INFORMATION_SCHEMA、PERFORMANCE_SCHEMA、SHOW STATUS、sys schema。

问题：

  • MySQL 的架构分哪几层？每层做什么？
  • SQL 的解析到执行的流程（解析 - 预处理 - 优化 - 执行）？
  • MySQL 如何和存储引擎交互（Handler 接口）？

二、存储引擎（重点：InnoDB）及差异

常见引擎

  • InnoDB（事务、安全、外键、MVCC）——默认引擎。支持行级锁、MVCC、崩溃恢复（redo/undo、doublewrite）。
  • MyISAM（非事务、表级锁、快速读）——适用于读多写少的场景（历史）。
  • Memory（内存表，非持久）——速度快，重启丢失数据。
  • NDB/Cluster（分布式、高可用）——适用于电信等实时场景。
  • Archive、CSV、Federated、Blackhole 等少见用途引擎。

InnoDB 关键特性

  • 聚簇索引（Clustered Index）：主键索引中包含整行数据；二级索引包含主键指针。
  • MVCC（多版本并发控制）：通过 undo log 提供一致读（consistent read），支持非阻塞读取（快照读）。
  • 事务日志：redo log（预写日志用于恢复）、undo log（用于回滚与 MVCC 读视图）。
  • 缓冲池（InnoDB Buffer Pool）：缓存数据页与索引页，关键性能点。
  • 双写缓冲（doublewrite buffer）：防止部分页写入导致页损坏。
  • 自适应哈希索引（AHI）、插入缓冲（change buffer） 等优化结构。
  • 行级锁：记录锁、间隙锁（gap lock）、next-key lock。
  • 崩溃恢复：基于 redo log + doublewrite + undo 进行恢复。

面试可能问：

  • InnoDB 和 MyISAM 的主要区别？
  • InnoDB 怎么保证事务的持久性？（redo + doublewrite + fsync）
  • InnoDB 的聚簇索引如何影响二级索引？
  • MVCC 的实现细节（读视图、undo log、事务隔离）？

高质量回答要点：

  • MyISAM 无事务，表级锁，支持 FULLTEXT（旧版本），恢复能力弱；InnoDB 支持事务、外键、行级锁，崩溃恢复严格。
  • InnoDB durabilty：事务 commit 写 redo log（预写），并最终刷写到磁盘；双写缓冲保护页完整性；checkpoint 控制脏页刷新；binlog 用于复制与持久化操作序列（注意 binlog_format 区别）。
  • 聚簇索引：主键是叶子节点包含整行。二级索引用主键回表（因此主键选择影响性能和空间）。

三、存储格式、页、表空间（细节）

页与行

  • InnoDB 页大小默认 16KB（可配置），页是 I/O 单位。
  • 页包含行记录、插入缓冲、空闲空间等。
  • 行格式（Compact, Redundant, Dynamic, Compressed）。
  • 行溢出（BLOB/TEXT） 存储在溢出页，叶子页中保存指针。

表空间

  • 系统表空间 ibdata1（历史上包含数据字典、undo，现代也支持 file-per-table）。
  • innodb_file_per_table：每个表一个 .ibd 文件，便于回收空间与表迁移。
  • Undo tablespaces（8.0+）单独管理 undo 数据。
  • doublewrite buffer：写入 doublewrite 区域再写入表空间。

面试可能问：

  • 页结构、行的存储格式、BLOB 如何存储？
  • innodb_file_per_table 的利弊？
  • redo/undo 在磁盘上的存储与作用？

回答要点：

  • 页是 16KB，行存储有记录 header + data。BLOB 在溢出页，只在行里存指针。
  • innodb_file_per_table=ON 好处：空间释放、独立表迁移、备份灵活；坏处：可能管理复杂、表空间碎片。
  • redo 用于重做 committed 事务；undo 用于回滚与构建 MVCC 快照。

四、事务与隔离（MVCC、隔离级别、异常）

事务特性（ACID）

  • Atomicity、Consistency、Isolation、Durability。

隔离级别（SQL 标准）

  • READ UNCOMMITTED（脏读）
  • READ COMMITTED（不可重复读）
  • REPEATABLE READ（默认 InnoDB：避免不可重复读，通过 MVCC 解决，但会有幻读通过 next-key lock 处理）
  • SERIALIZABLE（最高，强锁）

InnoDB MVCC

  • 读取分为两类：一致性读取（snapshot read） 和 当前读取（current read）。
  • 一致性读从 undo log 获取快照版本（不加锁）；当前读（如 SELECT … FOR UPDATE）会加锁。
  • Read View（读视图）：记录哪些事务是可见的（undo 被保留直到没有事务需要它）。
  • 幻读：REPEATABLE READ + InnoDB 的 next-key lock + gap lock 可以防止幻读（在可重复读实现中）。

面试问法：

  • MVCC 是如何实现的？read view 是什么？
  • 各隔离级别带来的并发问题（脏读、不可重复读、幻读）举例。
  • 为何 InnoDB 默认为 REPEATABLE READ 而不是 Serializable？
  • 如何避免幻读？什么时候会发生死锁？

回答要点：

  • 描述 undo log、read view、version chain 的交互：写操作在 undo 中保留旧版本；读操作通过 read view 确定可见版本。
  • 举例说明脏读/不可重复读/幻读。
  • InnoDB 选 REPEATABLE READ 是权衡性能与一致性；Serializable 性能开销大。
  • 幻读可通过加锁（SELECT … FOR UPDATE）、使用 SERIALIZABLE，或使用 gap locks 来应对。

五、锁机制（行锁、表锁、意向锁、MDL、死锁）

锁种类

  • 表级锁（MyISAM / explicit LOCK TABLES）
  • 行级锁（InnoDB）：记录锁（record lock）、间隙锁（gap lock）、next-key lock（记录+gap）。
  • 意向锁（Intention Locks：IX/IS）：用于提升并发时的表/行混合锁协调。
  • 元数据锁（MDL）：DDL 与 DML 协调（防止正在使用的表被修改结构）。
  • 全局/元数据/metadata locks。
  • 应用层锁：GET_LOCK() / RELEASE_LOCK()（用户态互斥）。

死锁

  • InnoDB 使用死锁检测（等待图）并回滚代价较小事务；SHOW ENGINE INNODB STATUS 能看到死锁信息。
  • 预防死锁：保证加锁顺序、使用较短事务、避免用户交互中的长事务。

面试问法：

  • 解释 next-key lock、gap lock、record lock 的用途与区别。
  • 为什么会出现死锁？如何诊断和优化？
  • 意向锁的作用是什么？

回答要点：

  • next-key lock = record lock + gap lock，用于防止幻读（阻止插入到某个间隙）。
  • 意向锁是表级的锁标志（在事务要加行锁时表上会设置 IX/IS），帮助存储引擎快速判断表级锁冲突。
  • 通过 innodb_print_all_deadlocks=ON、SHOW ENGINE INNODB STATUS、performance_schema 查看死锁原因；解决策略：短事务、合理索引、固定加锁顺序、升降隔离级别等。

六、索引（种类、原理、优化、常见误区）

索引类型

  • B+树索引（默认）：主键（聚簇）/非主键（辅助）索引，范围/排序良好。
  • 哈希索引：Memory 引擎的哈希、InnoDB adaptive hash（内存结构），只用于等值查找。
  • 全文索引（FULLTEXT）：文本搜索（MyISAM / InnoDB 支持）。
  • 空间索引（R-tree）：GIS 类型。
  • 倒排索引（内部实现 fulltext）。

索引设计原则

  • 选择高选择性列建索引。
  • 组合索引遵循最左前缀原则（leftmost prefix）。
  • 索引覆盖（covering index）：查询列完全被索引包含，不需回表（index-only）。
  • 避免在索引列上做函数/类型转换（会导致索引失效）。
  • 小心 ORDER BY 与 GROUP BY 使能索引排序。
  • 避免过多索引影响写入性能与空间。

索引访问类型（EXPLAIN 输出要熟悉）

  • index, range, ref, eq_ref, const, system, all（全表扫描）。
  • Using index（覆盖索引，避免回表）、Using where、Using temporary、Using filesort 等。

常见误区

  • “索引越多越好”→ 写入成本与维护成本高。
  • LIKE '%abc' 无法使用 B+树前缀索引。
  • OR 语句可能导致索引失效（可用 UNION 或索引合并）。

面试问法：

  • B+树为什么适合数据库索引？B+树 vs B树 区别？
  • 说明最左前缀原则、覆盖索引、回表。
  • EXPLAIN 看懂 type=ref、Using filesort、Using temporary 的含义和优化方法。
  • 为什么 ORDER BY 能用索引？

回答要点：

  • B+树所有值都在叶子节点，内节点仅为路由，叶子节点链表便于范围扫描；B树叶子与内节点都存值，分页 I/O 不如 B+树高效。
  • 最左前缀：复合索引 (a,b,c) 可用于查询 a、a,b、a,b,c；不能用于单独 b 或 c。
  • Using filesort 表示需要额外排序（可能磁盘），优化：创建合适联合索引或调整查询以避免 filesort。
  • ORDER BY 可以使用索引当查询顺序与索引顺序一致且没有 additional columns breaking coverage。

七、查询优化器（原理、成本模型、常见问题）

Optimizer 任务

  • 选择访问路径（索引或全表）
  • 选择 join 顺序与 join 算法（nested loop、hash join since 8.0）
  • 选择执行方法（index scan, range scan, index merge）
  • 统计信息驱动（histogram、cardinality）

常见优化点

  • 使用 EXPLAIN / EXPLAIN ANALYZE（8.0+）查看实际执行时间与行数。
  • 避免 SELECT *，优先列出需要列。
  • 使用合适的索引（联合索引、覆盖索引）。
  • 把常用的子查询改为 JOIN 或者使子查询可被下推（optimizer improvements）。
  • 避免不必要的排序、临时表：使用索引排序或 rewrite query。
  • 分页优化（大页码要用 ID 游标/seek 方法代替 offset-limit）。
  • 使用 ANALYZE TABLE 更新统计信息。

面试问法：

  • EXPLAIN 的各字段含义：type、possible_keys、key、key_len、ref、rows、Extra？
  • 如何优化慢查询？举组件和流程（定位、索引、重写、缓存、架构）。
  • Join 顺序与 join 算法的选择依据是什么？
  • 为什么有时索引没被使用？

回答要点：

  • 解释每个 EXPLAIN 字段，rows 是估算行数，key_len 表示使用索引的字节数。
  • 优化流程：捕获慢 query -> EXPLAIN -> 建索引或重写 -> 添加缓存 / 读写分离 / 分库分表 -> 再做压力测试。
  • Join 算法：nested loop 对小表驱动大表好，hash join（8.0+）对大表 join 有优势。代价模型由统计信息决定。
  • 索引不被使用：是因为类型转换、函数、low selectivity、ORDER BY mismatch、查询语法（OR）、统计信息过时等。

八、执行计划与 EXPLAIN 深入（实战）

要掌握的命令

  • EXPLAIN SELECT ...;
  • EXPLAIN FORMAT=JSON SELECT ...;（更详尽）
  • EXPLAIN ANALYZE SELECT ...;（8.0+，显示实际执行时间/行）
  • SHOW PROFILE（旧，较少用）
  • OPTIMIZER_TRACE（诊断优化器决策）

看点与优化建议

  • 关注 rows（估计） vs 实际扫描行数差异 → 更新统计或改写查询。
  • Using filesort 与 Using temporary 尽量通过索引避免。
  • index_merge 有时不是最优（对比实际执行时间）。
  • ref vs eq_ref：eq_ref 更好（唯一键匹配）。

九、复制（Replication）与高可用

复制类型

  • 基于二进制日志的主从复制（Asynchronous）：主写 binlog、从读取并回放（可能延迟）。
  • 半同步复制（Semi-synchronous）：主等待至少一个从确认接收（非完全提交确认），减少丢数据概率。
  • GTID（全局事务 ID）：事务唯一 ID，用于 failover 和自动恢复。
  • Group Replication / InnoDB Cluster（基于 Group Replication）：多主 / 可自动仲裁，提供一致性（Paxos/Raft-like）。
  • MySQL NDB Cluster：真正分布式存储引擎。
  • 主从拓扑：一主多从、多主（双主）——注意冲突解决和延迟。

binlog 格式

  • STATEMENT：记录 SQL 语句（小，但可能不确定性）。
  • ROW：记录行变化（最安全，复制精确，但日志大）。
  • MIXED：两者混合，优化选择。

延迟和一致性

  • 异步复制存在数据丢失窗口，半同步降低但不完全消除。
  • GTID 便于切换主/从、自动化 failover。

面试问法：

  • MySQL 复制原理（io thread & sql thread）？
  • binlog row vs statement 区别？
  • GTID 如何工作？如何做主从切换？
  • 如何实现高可用（自动 failover）？

回答要点：

  • 复制包括：主端写 binlog，slave 的 IO thread 拉 binlog 写 relay log，再由 SQL thread 执行 relay log。
  • ROW 格式复制的是行级别事件，避免非确定性（如 NOW()），STATEMENT 小但风险高。
  • GTID 是 source_id:txn_id 的全局唯一标识，切换时只要保证 GTID 同步即可减少手动操作。
  • 高可用方案：主从 + 心跳 + 自动 failover（MHA, Orchestrator + ProxySQL）或使用 Group Replication / InnoDB Cluster。

十、备份与恢复（策略、工具）

备份方式

  • 逻辑备份：mysqldump、mysqlpump（可移植，慢）。
  • 物理备份：xtrabackup（Percona XtraBackup）做热备份（InnoDB），复制表空间文件快。
  • 快照：文件系统或云磁盘快照（需要一致性处理）。
  • Binlog-based point-in-time recovery（PITR）：物理备份 + replay binlog。

恢复考虑

  • 恢复时间（RTO）与数据丢失容忍（RPO）。
  • 恢复测试必做（常被忽视）。
  • 冷备份 vs 热备份权衡。

面试问法：

  • 如何设计备份方案？如何做 PITA（点时间恢复）？
  • xtrabackup 的工作原理（innodb 物理拷贝 + apply-log）？

回答要点：

  • 备份策略常用：全量周一次 + 增量/差异 + binlog 每日归档。恢复流程需要明确演练。
  • xtrabackup 做非阻塞拷贝，然后 apply log（redo）使备份一致；支持 streaming 增量。

十一、分区与分库分表（水平/垂直拆分）

分区（Partitioning）

  • 类型：RANGE, LIST, HASH, KEY, RANGE COLUMNS
  • 优点：管理大量数据（分区裁剪，便于删除旧数据）
  • 缺点：不能分散到多机器（仍在同一实例），复杂性高，索引限制（有时分区键必须在 where 子句中）

分库分表（Sharding）

  • 垂直拆分：按业务拆分表到不同 DB。
  • 水平拆分：按某字段（用户 id）拆成多个分片。
  • 中间件：应用层路由、Sharding Sphere、ProxySQL + application logic。
  • 数据一致性与跨分片事务复杂（两阶段提交 / XA / distributed transaction），多数场景用 BASE + 事务补偿 或 可靠消息 + 最终一致性方案。

面试问法：

  • 分库分表怎么做？如何保证跨分片事务一致性？
  • 分区和分库的对比？

回答要点：

  • 分区适合单实例内数据管理；分库能扩展到多机器。跨分片事务代价高，常用两段提交/分布式事务中间件或领域驱动设计避免跨分片事务，使用补偿事务和幂等设计。

十二、性能调优要点（参数、监控、瓶颈定位）

关键调参

  • innodb_buffer_pool_size：最重要，通常 60-80% 的可用内存（只在 DB 专机上）。
  • innodb_log_file_size、innodb_log_files_in_group：影响 checkpoint 和写入性能。
  • innodb_io_capacity / innodb_io_capacity_max：控制后台刷脏页速度。
  • innodb_flush_log_at_trx_commit：0/1/2 三档，权衡持久性与性能（1 最安全）。
  • max_connections、thread_cache_size、table_open_cache、innodb_thread_concurrency。
  • query_cache（已废弃，注意版本，MySQL8 已移除）——不要在写密集场景启用。
  • tmp_table_size / max_heap_table_size：内存临时表限制。

监控指标

  • Buffer pool hit ratio（Innodb_buffer_pool_read_requests / Innodb_buffer_pool_reads）
  • Dirty pages、IO wait、transaction rate、row lock waits、slow queries.
  • SHOW ENGINE INNODB STATUS、performance_schema、INFORMATION_SCHEMA.INNODB_*。

瓶颈定位流程

  1. 监控/报警识别问题（CPU/IO/Memory/Network）。
  2. 找到慢 SQL（慢查询日志）。
  3. EXPLAIN / PROFILE / ANALYZE 优化 SQL。
  4. 索引 / schema / rewrite / cache。
  5. 架构优化：读写分离、缓存、分库分表、队列削峰。

面试问法：

  • 当系统慢，你如何排查？举一步步流程与命令。
  • Buffer pool 命中率低如何处理？

回答要点：

  • 给出详细排查步骤（OS 层（iostat/top）、MySQL 层（SHOW PROCESSLIST、SHOW ENGINE INNODB STATUS、慢查询日志、performance_schema）、EXPLAIN）。
  • Buffer pool 命中率低：增大 buffer pool、检查大表扫描、索引缺失导致大量全表扫描。

十三、B+树、B树、哈希（理论与应用）

B+树 vs B树

  • B-tree：每节点存键值和数据。查找时数据可能位于内、叶节点。
  • B+树：非叶子节点仅存键和指向子节点的指针，所有数据都在叶子节点。叶子节点通过链表连接，便于范围扫描。
  • 为什么数据库用 B+树？
    • 叶子节点连续且链表便于范围查询与顺序访问。
    • 内节点小，能增加内存中一层索引效率（磁盘 I/O 少）。
  • 哈希索引：适合等值查找，不能范围查找，碰撞处理，Memory 引擎用到。

面试问法：

  • B+树的插入/删除对页分裂/合并的影响？
  • B+树为什么适合磁盘存储（IO 层考虑）？

回答要点：

  • 插入：找到叶子插入；若溢出分裂并向上调整；删除可能导致合并或借位。页分裂导致写放大和更多 IO。
  • B+树减少磁盘读：内节点驻留内存可快速导航到叶子；一次页读获取多个键/值数据。

十四、进程/线程管理（mysqld 模型）

线程模型

  • 每个客户端连接默认一个线程（old model），现代可以使用线程池插件（thread_pool）处理大量连接。
  • thread_cache_size 缓存线程减少创建开销。
  • 使用 epoll/kqueue 等 I/O 多路复用机制在 OS 层。

重要参数

  • max_connections：最大连接数（过高导致 OOM）
  • thread_cache_size：线程复用
  • table_open_cache、open_files_limit

面试问法：

  • MySQL 如何处理并发连接？线程池有何优点？
  • max_connections 过大有什么风险？

回答要点：

  • 线程池可以重用线程、控制并发执行线程数，避免大量线程竞争 CPU 和内存。max_connections 过大会导致内存和上下文切换开销。

十六、常见面试题（题目+要点答案）

我把最常被问的题列出来——面试中能直接背答案并扩展即可。

  1. MySQL 的事务隔离级别有哪些？分别会出现哪些并发问题？
    • 答：列出 4 个并说明脏读/不可重复读/幻读；解释 InnoDB 如何用 MVCC + gap lock 解决幻读。
  2. 事务提交时都发生了什么？
    • 答：写 redo log（WAL），如果 innodb_flush_log_at_trx_commit=1 则 fsync；写 binlog（若 sync_binlog=1 则也 fsync）；释放锁，更新状态。
  3. 主键选择如何选择？
    • 答：尽量单调递增、短（INT 比 UUID 好）、唯一、稳定。若是 UUID，考虑使用有序 UUID 或使用 DB-generated autoinc + sharding id。
  4. 聚簇索引的优缺点？
    • 答：优点：范围查找快、主键回表无额外开销；缺点：二级索引回表成本、主键变更代价大、插入可能导致页分裂。
  5. 解释 InnoDB 的 MVCC 实现。
    • 答：undo log 保存历史版本，读创建 read view 只读可见版本，写操作链上并生成 undo，读不阻塞写（除非 current read）。
  6. 如何解决慢查询（定性定量）？
    • 答：collect slow queries -> EXPLAIN -> add index / rewrite / cache / change schema -> measure -> repeat。列出命令与举例。
  7. 如何做主从切换（无缝或最小影响）？
    • 答：使用 GTID + 停写 + promote slave（或 Orchestrator 自动化），或使用半同步减少丢失窗口。演示步骤要点。
  8. 为什么索引没起作用？
    • 答：函数在列上、隐式类型转换、使用 OR、LIKE 前缀、范围查询导致后续列失效、统计信息问题、低选择性、索引未被覆盖。
  9. 如何避免死锁？
    • 答：短事务、固定加锁顺序、对热点行使用乐观锁或队列、索引优化避免范围锁、重试机制（捕获死锁后重试事务）。
  10. Explain 中的 type 字段代表什么？
    • 答：访问类型（system < const < eq_ref < ref < range < index < all），表示扫描效率，从 best 到 worst。
  11. 如何设计大表的分页？
    • 答：避免 OFFSET+LIMIT 在大页码，使用主键范围查询（seek method）或保持上次最后 ID 的游标分页。
  12. innodb_buffer_pool_size 如何设置？
    • 答：一般设置为 60~80% 的可用内存（若只运行 MySQL），并留空间给 OS 缓存与其他进程。
  13. 如何做在线模式变更（schema change）？
    • 答：使用 pt-online-schema-change 或 gh-ost 做无锁在线变更；MySQL 8 更多 DDL online 支持，但仍有限制。
  14. Explain JSON 输出怎么看？（实际执行计划）
    • 答：关注 cost_info、table、access_type、used_indexes、rows_estimate、messages。

（面试题远不止这些，关键是能根据问题把实现原理、常见问题、解决办法与命令结合起来说明。）

十七、常见错误、坑与注意事项（面试喜欢挖的地方）

  • 误用 UUID：UUID 导致随机插入，严重碎片化，写放大。解决：使用有序 UUID 或使用前缀字段做哈希。
  • 忘记索引覆盖回表成本：二级索引查出主键后回主键表查行，成本显著。
  • 使用 SELECT \* 导致不必要 IO。
  • 忽视长事务：长事务阻止 purge，导致 undo 文件增长与性能下降。
  • 误用 innodb_flush_log_at_trx_commit=2/0 在需要强持久性的场景。
  • 没有测试备份恢复流程——备份无用如果不能恢复。
  • 过度索引：写性能下降、更多维护与磁盘。

十九、架构级别的可用性与扩展方案

读写分离

  • Master 写、Slave 读，使用 ProxySQL / HAProxy / application routing。
  • 注意复制延迟导致读到旧数据（解决：读从优先级或事件时间线设计）。

负载均衡与故障转移

  • Orchestrator（自动化拓扑管理）、MHA、ProxySQL 与 Keepalived，配合心跳实现自动化 failover。
  • 使用 GTID 简化切换。

分布式事务与可靠消息

  • XA（两阶段提交）支持但复杂且性能差。
  • 常见设计是最终一致性：可靠消息 + 消息幂等 + 补偿事务。

缓存层

  • Redis / Memcached 做热点缓存（注意缓存失效策略和缓存击穿 / 穿透 / 雪崩 防护）。

  1. 先给结论，再解释原因，再给例子/命令（面试官喜欢结构化回答）。
  2. 关注权衡：每种方案都有利弊，列出代价（性能/一致性/复杂度/运维）。
  3. 用数据说话：给出常用参数与推荐值（如 buffer pool 设置策略）。
  4. 能写命令就写命令：在白板或远程面试中写出 EXPLAIN / SHOW 命令。
  5. 演示排错流程：现场讲一个“系统变慢”的排查流程，具体到命令与指标。
  6. 提到版本差异：MySQL 8 对 optimizer、hash join、窗口函数、JSON、CTE 支持等增强，说明你注意版本变化。

最后 — 面试真题演练（3 个综合题）

  1. 题目：系统突然出现大量 LOCK WAIT，影响写操作。请现场给出排查步骤与命令，并提出 3 种解决策略。
    • 答：列出：SHOW ENGINE INNODB STATUS\G（查看死锁/等待），SELECT * FROM INFORMATION_SCHEMA.INNODB_TRX、INNODB_LOCK_WAITS、SHOW PROCESSLIST、定位长事务/慢 SQL；解决：短事务/添加索引避免 full scan/杀掉阻塞事务并优化事务逻辑/使用更低隔离（READ COMMITTED）或改写 SQL。
  2. 题目：为什么 SELECT … LIMIT 1000 OFFSET 100000 很慢？如何优化？
    • 答：OFFSET 会扫描并跳过前 100k 行，I/O 大。优化：使用索引 seek（WHERE id > last_id LIMIT 1000），或按索引范围分页、按时间分片，或利用 keyset pagination。
  3. 题目：如何做主从切换以保证最小数据丢失？
    • 答：开启半同步，等待从机接收并写 flush relay log（或确认），在切换时使用 GTID：stop writes -> ensure slave caught up (SHOW SLAVE STATUS，Seconds_Behind_Master=0) -> promote slave -> redirect writes，或使用 Orchestrator 自动 failover，并考虑 slave read-after-write consistency。
