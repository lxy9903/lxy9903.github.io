Elasticsearch详解

[TOC]

1. ES 是什么？适用场景是什么？

Elasticsearch = 分布式搜索引擎 + 分布式文档数据库。

核心特点：

  • 全文检索（倒排索引）
  • 支持结构化 + 非结构化数据
  • 可横向扩容（天然分布式）
  • 高性能写入（日志、监控）
  • 实时性近似（默认 1s 刷盘）

最适合场景：

  • 日志（ELK）
  • 监控（Prometheus → ES）
  • 搜索服务（商品搜索、文本检索）
  • 用户画像、埋点行为查询
  • 智能推荐的向量搜索（结合 HNSW + KNN）

2. ES 的核心概念

ES MySQL 描述
index database 索引
type table （已废弃）
document row 数据行
field column 字段
shard 分片 水平分布数据
replica 副本 高可用 + 读扩容

3. 倒排索引（全文检索的核心）

MySQL 索引：B+ 树 → 适合精确匹配

ES 索引：倒排索引 → 适合搜索、模糊匹配

示例文档：

Doc 1: “I love Java and Kafka”
Doc 2: “Java engineering is awesome”

倒排索引结构：

term doc list
java [1,2]
love [1]
awesome [2]

特性：

  • 适合“分词”
  • 查找谁包含某个 term 很快
  • 适合 query parser、scoring（TF-IDF/BM25）

4. ES 写入流程（核心面试题）

写入流程（非常经典的面试题）

详细流程：

  1. 客户端写入 document
  2. 协调节点根据 routing 找到目标 primary shard
  3. primary shard：
    • 写入 memory buffer
    • 写入 translog（WAL，崩溃恢复）
  4. 每 1 秒自动 refresh，生成新的 segment（可搜索）
  5. 异步复制到 replica shard

保证：

  • 1 秒实时性
  • 片内顺序写
  • 跨分片副本复制

5. ES 查询流程

两个阶段：

  • query phase：分片内部查
  • fetch phase：收集真实文档内容

6. 分片设计（Shard）

一个 Index 内部会拆成多个 shard。

为什么分片？

  • 提升容量（每个 shard 类似一个小 lucene）
  • 提升查询吞吐（并行）

分片数一般不能改，但可以通过 rollover、alias 实现扩容

7. 副本（Replica）与高可用

Replica Shard 用于：

  • 高可用（primary 挂了自动切换）
  • 读扩容

8. ES 容错机制（分布式核心）

  • master 选举（minimum_master_nodes）
  • 分片的自动迁移与恢复
  • translog → shard recovery
  • quorum 写确认

master 节点不负责写，只负责：

  • 元数据
  • shard 分配

9. ES 集群的三种节点类型

节点类型 作用
master 节点 选举、元数据、分片调度
data 节点 存数据、查数据、建索引
coordinating 节点 路由请求、聚合结果

10. ES 数据建模（Mapping）

关键字段类型：

  • keyword：不分词
    • 适合 ID、精确匹配、聚合
  • text：分词
    • 适合 full-text search
  • date
  • nested（复杂对象）
  • geo_point

常见坑：

  • text 字段默认不会聚合
  • keyword 默认最大 256 字符（过长会被拒绝）
  • 数组不需要 declare array（天然支持）

11. ES 性能优化（高频面试点）

写优化

  • bulk 批量写入（1000-5000 条）
  • 减少 refresh 次数（默认 1 秒）
  • 调整副本数（写前临时设置为 0）

读优化

  • 打开 routing（避免跨 shard 搜索）
  • 使用 keyword 代替 text
  • 关闭 wildcard / regexp 之类的慢查

分片优化

  • shard 不要太多，推荐每个 shard 20-50 GB
  • 小 shard 多了会导致调度压力大

12. ES 的强点 & 弱点

强点

  • 搜索极快（倒排索引）
  • 分布式天然支持
  • 日志场景超合适

弱点（必须知道，面试会问）

❌ 不是 OLTP 系统
❌ 不支持事务
❌ 不能频繁更新（segment append-only）
❌ 不适合高写扩散（大量 update/delete）
❌ 不适合精确分析（需要使用 column store）

13. ES 常见问题 & 解决方案

① ES 数据更新很慢/很耗资源

原因：segment append-only
解决：用 upsert + 不频繁更新 + TTL 滚动索引

② ES 存储容量不断膨胀

解决：ILM（Index Life Management）

③ ES 数据不一致（最终一致）

因为 replica 异步

④ 热点分片

大量写落到某个 shard
解决：routing + ES roll-over + hash 扩散

14. ES 与数据库对比

功能 ElasticSearch MySQL
检索 模糊搜索、全文搜索 精确检索
数据模型 文档（JSON） 行式
事务 弱一致 强一致
写 append-only（快） 随机写
读 分布式并行 单点或读副本

15. 一句话总结 ES

ES 不是数据库，它是一个“可横向扩展的搜索引擎 + 日志分析引擎”，核心是倒排索引，适合读多写少的模糊查询场景。
