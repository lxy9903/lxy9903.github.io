数据库隔离级别详解

[TOC]

一、什么是数据库隔离级别？

隔离级别的核心目标：

  • 并发性能（吞吐） 和 数据一致性（正确性） 的权衡
  • 防止多事务并发访问同一数据时产生异常
  • 不同数据库采用不同的实现机制（锁、MVCC、版本链、快照等）

典型并发异常：

异常 含义
脏读 Dirty Read 读到别人未提交的数据
不可重复读 Non-repeatable Read 同事务两次读同一行，结果不同
幻读 Phantom Read 同事务两次查询相同条件，返回的结果行数不同

二、四种隔离级别详解

1️⃣ Read Uncommitted（读未提交）

  • 可能出现 脏读 / 不可重复读 / 幻读
  • 几乎不会用于正式环境

2️⃣ Read Committed（读已提交）

  • 不会脏读
  • 可能出现不可重复读、幻读
  • 每次读都获取当下最新快照（Oracle、PG 等采用）

3️⃣ Repeatable Read（可重复读）

  • 同一事务多次读结果一致
  • 防止不可重复读
  • MySQL 采用 MVCC + 间隙锁 防止幻读

Oracle 的 RC ≈ MySQL 的 RR（因为一致性读更强）

4️⃣ Serializable（串行化）

  • 完全串行执行
  • 最安全，但性能最低
  • 业务很少使用

三、不同数据库的默认隔离级别

数据库 默认隔离级别 是否支持 MVCC 特点
MySQL（InnoDB） Repeatable Read ✔ 幻读通过间隙锁解决
Oracle Read Committed ✔ 强大的 UNDO + 一致性读，没有锁读
PostgreSQL Read Committed ✔ 强 MVCC，无间隙锁
MongoDB Read Committed（本质文档级锁 + WiredTiger MVCC） ✔ 单文档级事务天然一致
Elasticsearch 无事务隔离级别 ✘ 近实时搜索，最终一致性

四、MySQL、Oracle、PG、MongoDB、ES 隔离级别与实现机制对比

1. MySQL（InnoDB）

默认：Repeatable Read

  • MVCC 一致性视图 + undo log
  • 为防止幻读 → 间隙锁（Gap Lock）、Next-Key Lock → 会锁住某区间，导致写冲突增加，性能降低

优点：幻读被彻底解决

缺点：锁冲突较多，写性能较弱

2. Oracle

默认：Read Committed（读一致性非常强）

Oracle 的一致性读（Consistent Read）原则：

  • 读数据时不加锁
  • 始终通过 UNDO 构建“读时间点快照”
  • 即使是 Read Committed，也不会产生不可重复读对业务的危险版本

❓为什么 Oracle 的 RC 比 MySQL 的 RR 更强？

因为 Oracle RC 是：视图级一致性（Statement-level Consistent Read）

而 MySQL RR 是：事务级一致性（但依赖 MVCC + Gap Lock）

Oracle 的 RC：

  1. 读时不锁住行（高并发）
  2. 自动从 UNDO 构造历史版本（稳定一致）
  3. 写之间采用行锁，不产生 gap lock（写性能更强）

企业金融行业大量使用 Oracle，是它 RC 的强一致性 + 高写性能带来的优势

3. PostgreSQL

默认：Read Committed

采用 MVCC，无间隙锁：

  • 每行记录包含 xmin、xmax 版本号
  • 不阻塞读
  • 写写冲突会由 MVCC 自动处理

比 MySQL 更自然、简单，性能更好。

4. MongoDB

默认类似 Read Committed

机制：

  • 文档级锁
  • WiredTiger MVCC（读旧版本视图）
  • 多文档事务支持 Snapshot isolation

但使用场景更偏向 NoSQL，高并发写性能好。

5. Elasticsearch

无事务隔离级别

  • 近实时搜索（NRT）
  • 数据写入后 1 秒左右可见
  • 底层采用 Lucene 段文件 + refresh 机制
  • 一致性模型：最终一致性（Eventual Consistency）

五、MVCC - 多版本并发控制

原理：

  1. 版本号 / 时间戳：每个事务有一个唯一的时间戳（或事务 ID），每行数据记录它的创建时间/修改时间。
  2. 读操作
    • 读取符合自己事务时间点的数据版本 → 一致性读（Consistent Read）
  3. 写操作
    • 创建新版本
    • 并不会覆盖旧版本，直到事务提交才更新可见性
  4. 清理旧版本：通过后台线程或自动清理（VACUUM / Undo / Purge）

优点：

  • 高并发场景下，读写不阻塞
  • 保证事务隔离性（如 Snapshot Isolation）

缺点：

  • 占用存储空间（多版本）
  • 需要清理旧版本，否则膨胀
  • 实现复杂

不同数据库MVCC：

数据库 MVCC 实现方式 特点
MySQL（InnoDB） 隐藏列 + Undo Log - 每行记录两个隐藏字段：trx_id、roll_pointer - 一致性读直接读取 Undo 版本 - 更新不阻塞读 - 读写不阻塞，写写可能冲突
PostgreSQL 真正的多版本存储 MVCC - 每行存储 xmin（创建事务）、xmax（删除事务） - 读操作通过事务 ID 选择可见版本 - 更新生成新行版本，旧版本由 VACUUM 清理 - 写操作不阻塞读
Oracle Undo + MVCC - 每次读创建快照（Read Consistency） - 读操作使用 Undo 数据回溯 - 写操作产生新版本 - 默认 Read Committed 隔离级别
MongoDB 文档级 MVCC - WiredTiger 引擎支持 Snapshot Read - 单文档事务支持 ACID - 并发读不阻塞写，文档级别隔离
ES（Elasticsearch） Lucene Segment + SeqNo - 每次写入创建新段（Segment） - 读操作基于段快照 - 类似 MVCC，但主要为搜索，不适合事务场景

五、为什么 Oracle 默认 Read Committed 比 MySQL 默认 Repeatable Read 还强？

维度 MySQL RR Oracle RC
幻读 通过 gap lock 解决 通过 UNDO 构造历史快照解决，不靠锁
并发写性能 较低（gap lock 多） 高（无 gap lock）
一致性读强度 事务级一致视图 语句级一致视图（更自然，稳定）
加锁策略 行锁 + 间隙锁 行级锁（无间隙锁）

Oracle RC 实际上是一种更先进的隔离机制： 不通过加锁，而是用 UNDO 构造历史快照 → 实现更高并发 + 强一致性。

六、Oracle RC 会不会在银行扣款类业务出问题？

不会。

因为银行核心业务会加：

  • 明确锁（SELECT … FOR UPDATE）
  • 乐观锁版本号
  • 去重表、流水号机制
  • 业务 idempotent 设计
  • 分布式锁

Oracle RC 的 MVCC 只影响读，不影响写的锁机制：

  • 更新记录时，Oracle 使用 行级锁（Row Lock）
  • 不允许两个事务同时修改同一行
  • 银行扣款是强写操作 → 不受 RC 的一致性读影响

因此： Oracle RC 完全能保证银行类敏感数据安全。

七、什么时候 Read Committed 不适合？

  • 需要“全事务一致视图”的长事务
  • 大范围范围查询 + 写并发（可能看到新行）
  • 复杂审计、取证场景（需要时间点一致性）

此时应使用：

  • Oracle：Serializable
  • MySQL：Repeatable Read 或加锁读

八、一句话总结

数据库 默认级别 优势
Oracle：RC 强一致性读 + 性能最强 + 无 gap lock = 金融行业王者
MySQL：RR 普适，但依赖 gap lock，写性能差
PG：RC MVCC 实现纯粹清晰，性能优雅
MongoDB：RC 文档级强事务，对整体隔离要求低
ES：无隔离 适合搜索，不适合强事务
