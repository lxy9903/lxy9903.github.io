MySQL 分库分表方案

[TOC]

一、为什么要分库分表？

当出现以下问题 → 必须分库分表：

痛点 现象
单表太大 DML 慢、索引失效、备份恢复慢
单库 QPS 太高 主库扛不住，连接耗尽
热点数据量巨大 单机 CPU、IO、网络瓶颈
单机存储不足 数据持续增长

一般的数据量吞吐阈值（经验值）

  • 单表行数 > 2000 万 → 建议分表
  • 单库 QPS > 5000 → 建议分库
  • 单表超过 50GB → 查询性能严重下降

二、分库 vs 分表区别

方案 改善问题 核心作用
分表（水平拆分） 表太大 降低单表的数据量
分库（水平拆分） 单库压力太大 扩展 QPS/连接数/IO
分库分表 数据量大 + 并发高 大型互联网系统常用

三、分库分表整体方案

方案 1：范围（Range）分片

优点

  • 容易维护
  • 数据自然分布（按时间、用户 ID）

缺点

  • 非均匀：早期库会巨大（时间倾斜）
  • 热点集中：例如当天流量全部写入最新分片

方案 2：哈希（Hash / Mod）分片（最常用）

优点

  • 数据均匀
  • 方案简单可靠

缺点

  • 扩容难 → 改变模数会导致全量迁移（最致命）

方案 3：一致性 Hash

用于解决 Hash % N 扩容需要迁移大量数据 的问题。

优点

  • 扩容只迁移 1/N 数据（理论）

缺点

  • 实现更复杂
  • 不适合极端热点场景

方案 4：按时间分表（日志 / 账单 / 订单常用）

例如每月一张表：

优点

  • 易维护、冷热数据分离
  • 单表永远可控

缺点

  • 不适用于按用户/ID 查询
  • 需要跨表查询

方案 5：混合分片

例子：
大用户量 → 哈希分库
订单量巨大 → 按月分表

五、分布式 ID 方案

分库分表后主键 不能用 MySQL 自增，否则不同库会冲突。

推荐如下：

方案 特点
Snowflake（大厂通用） 毫秒级，趋势递增，不依赖 DB
Leaf（美团） DB 号段模式，绝对可靠
Redis 自增 简单但不强一致
UUID 无序，索引性能差，不建议

主流 → Snowflake + 时间回拨保护

六、最难的问题：跨库 JOIN、COUNT、分页、排序

分库分表之后 MySQL 就不支持 JOIN、ORDER BY、LIMIT 了，你需靠业务或中间件解决。

下面整理生产方案：

1）跨库 JOIN 解决方案

方案 说明
A. 业务层 JOIN 基础表（如 user）放独立库
B. 冗余字段 冗余 user_name、category_name
C. ES 或 ClickHouse 查询 用于多维度、分页、搜索

真实互联网常用：

👉 分库分表只是写库，查库一般上 ES

2）跨库分页

做法：

  1. 每个库查 limit (pageSize × 5)
  2. 汇总结果
  3. 再统一排序
  4. 最后取 pageSize 条

也叫 多路归并分页（merge-sort pagination）

3）跨库 COUNT

法 1：每个库 count，最后累加

法 2：每天/每小时维护统计表（异步）

4）跨库 ORDER BY

每个库 local sort → merge sort → 再裁剪
