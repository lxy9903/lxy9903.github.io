Kafka — 基础知识

一、Kafka 基础与整体架构

Kafka 是一个 高吞吐、分布式、可扩展、可持久化 的消息流平台，核心特性：

  • 高吞吐：顺序写磁盘 + PageCache 零拷贝
  • 分区并行：partition 并发处理
  • 水平扩展：broker 任意扩容
  • 高可用：基于 副本 + ISR + Controller 的复制机制
  • 持久化：segment 文件顺序写
  • 支持流处理：Kafka Streams
  • 支持批处理与订阅模型：consumer group

Kafka 三大核心角色：

1. Producer（生产者）

  • 支持批量、压缩、异步发送
  • 参数：batch.size、linger.ms、compression.type 影响性能

2. Broker（服务器）

  • Topic → Partition → Segment
  • 高效的 顺序写磁盘
  • Zero-copy 提升发送性能

3. Consumer（消费者）

  • 通过 Consumer Group 实现水平扩展
  • 自动提交/手动提交 offset
  • 支持多种订阅方式（range、round-robin、sticky）

4. Zookeeper（旧架构）/ KRaft（新架构）

  • 存储元数据
  • Leader 选举
  • Partition 分配、Topic 创建、ISR 管理
    Kafka 3.x 后进入 KRaft 时代：
  • 不再依赖 Zookeeper
  • Kafka 自身存储元数据
  • 一组 Controller 选举

Kafka 场景：

  • 数据采集（日志、行为）
  • 异步削峰解耦
  • 流式计算（Flink/Spark）
  • 订单、支付、分布式事件
  • CDC（MySQL → Kafka → Downstream）

二、Kafka 存储、分区、副本、ISR 深度原理

Kafka 的核心就是 分区 + 顺序写 + 副本。

1. Topic → Partition → Segment 结构

Partition 是 Kafka 并行度单位

  • 每个 partition 是一个 有序、不可变 的消息队列
  • 只能追加写入
  • 可配置副本数（replication.factor）

Segment 是磁盘文件

一个 partition 会拆成多个 segment 文件：

好处：

  • 文件分段可快速删除
  • 避免文件过大难以管理
  • 高效顺序写

2. Zero Copy + Page Cache

Kafka 默认不读取整个 log 文件，而是使用：

  • sendfile 系统调用
  • PageCache 做文件系统缓存
  • 数据不需要在用户态和内核态之间来回复制

Kafka 的高性能来源之一。

3. 副本机制（Replication）

每个 partition 有：

  • leader（负责读写）
  • follower（复制 leader）

4. ISR 列表

ISR（in-sync replica）：
与 leader 保持同步的副本集合。

Kafka 认为只要 follower：

  • 延迟不超过 replica.lag.time.max.ms
  • 未落后太多

就属于 ISR。

ISR 不包括所有副本，这样可以保证：

  • leader 切换快
  • 不拖慢整个集群

5. ack 机制与数据可靠性

生产者发送消息时可设置：

  • acks=0：最快，不可靠
  • acks=1：leader 写入成功即可
  • acks=all / -1：leader + ISR 全部写入成功（最安全）

6. Leader 选举与 Controller 原理

Kafka 通过 Controller（集群元数据管理者）管理：

  • partition leader 选举
  • broker 上下线
  • ISR 变化
  • Topic 创建、分区扩容

KRaft 时代后，元数据不再依赖 Zookeeper，而是：

  • 存储在内部 topic：__cluster_metadata
  • 使用 Raft 算法保证一致性
  • 由 Controller quorum 选主

三、Kafka 消费机制、Offset、重平衡、消费语义

Kafka 的消费机制是面试高频。

1. Consumer Group

一个 group 里的消费者：

  • 共同消费一个 topic
  • 每个 partition 只会被一个 consumer 消费
  • 多个 consumer 才能并行处理

2. Offset 存储机制

新版本 Kafka 将 offset 存储在内部 topic：

而不是 Zookeeper。

offset 的提交方式：

  • 自动提交：容易丢消息
  • 手动提交：更安全
    • commitSync（阻塞）
    • commitAsync（高性能）

3. Rebalance（再平衡）

触发条件：

  • 新 consumer 加入
  • consumer 崩溃
  • partition 数变化
  • topic 增减

问题：

  • 再平衡期间 partition 无法消费
  • 性能损耗

解决方案：

  • StickyAssignor：最小化 repartition
  • Heartbeat + sessionTimeout 调优
  • 增加 partition 让负载更均衡
  • Kafka Streams 有更优雅的协调逻辑

4. 消费语义

Kafka 理论上支持：

  • 至少一次（默认）
    • 有可能重复消费
  • 至多一次
    • 有可能丢消息
  • 恰好一次（EOS）
    • 通过 Producer Id + Transaction 保证
    • 适合金融、支付场景

5. Exactly Once 的底层原理（面试超爱问）

Kafka 0.11 引入 Transaction + idempotent producer：

  • PID（唯一生产者 ID）
  • Sequence number
  • Transaction marker 写入特殊日志

保证：

  • 多次重试不会产生重复消息
  • 消费到处理 + 写回 Kafka 也能做到 exactly once

这是分布式系统里极难的能力。

四、Kafka 高级特性、调优、故障处理、面试核心

1. 性能优化（Producer / Broker / Consumer）

Producer 优化

  • linger.ms：延迟发送增大批次
  • batch.size：增加批处理大小
  • compression.type：snappy/lz4/zstd
  • acks=1：更快（低可靠）
  • acks=all：高可靠

Broker 调优

  • 合理分区数（不要太多）
  • 增大页缓存
  • replica.lag.max.ms 调优避免 follower 脱 ISR
  • 适当开启 auto.create.topics
  • 调整 log.retention.ms 空间回收策略

Consumer 优化

  • max.poll.interval.ms → 防止触发 rebalance
  • max.poll.records → 增加批消费
  • 手动提交 offset（更安全）

2. 生产中的问题及解决方案

⚠️ 1. 消息乱序

发生原因：

  • 多 partition
  • 重试
  • 网络 timeout
  • 重平衡

解决：

  • 使用 key 分区，同 key 发送到同 partition
  • 使用单 partition（牺牲吞吐）
  • 使用 Kafka Streams / Flink 做窗口排序

⚠️ 2. 消息丢失

可能原因：

  • acks=1
  • ISR 不足
  • 未 commit offset
  • 主从切换

解决：

  • acks=all
  • min.insync.replicas=2
  • 手动提交 offset
  • 开启事务（exactly once）

⚠️ 3. 消息重复

原因：

  • Producer 重试
  • Consumer 重复提交 offset

解决：

  • 幂等生产者（enable.idempotence=true）
  • 业务端做幂等（Redis、数据库唯一索引）

3. Kafka 在业务中的最佳实践

典型场景：

日志采集

Kafka + Filebeat → ES / Clickhouse

主站事件驱动

下单 → Kafka → 支付系统 / 库存系统 / 推荐系统

秒杀削峰填谷

请求写入 Kafka → Worker 均匀消费

MySQL Binlog → Kafka → Flink → Redis

支持实时计算、投递、分布式缓存一致性
