Kafka — 基础知识与核心原理

[TOC]

一、Kafka 基础与整体架构

Kafka 是分布式的、支持 高吞吐 + 可持久化 + 副本高可用 的消息系统。

1. 三大核心角色

Producer

  • 批量发送、压缩、异步/同步发送
  • 支持 重试 + 幂等 + 事务

Broker

  • 存储数据：Topic → Partition → Segment
  • 顺序写磁盘 + 零拷贝

Consumer

  • 使用 Consumer Group 提升消费能力
  • offset 存于内部 topic __consumer_offsets

2. Kafka 架构图

二、Kafka 数据存储结构

Kafka 的核心：追加写入 + 分区存储 + 分段文件。

1. Topic / Partition / Segment

特点：

  • Partition = 有序、不可变的消息队列
  • 每次写入都是顺序 append
  • Partition 会被切分成多个 segment（默认 1GB）

2. 顺序写提升吞吐的原因

随机写：磁盘寻道能力差
顺序写：磁盘每秒可写上百 MB

Kafka 通过顺序写实现：

  • 吞吐比传统消息队列高 10～30 倍

3. Segment 的具体存储内容与文件结构

Kafka 每个 segment 实际包含 3 种文件（同一前缀）：

文件 作用
xxx.log 真正存放消息数据，顺序追加
xxx.index offset → 物理位置映射（稀疏索引）
xxx.timeindex timestamp → offset 映射，用于按时间查找

index 是稀疏的，不是每条消息都索引，只存每隔 N 条，减少内存占用。

Kafka 默认数据目录（log.dir）：

一个 partition 对应一个文件夹，便于分布式扩展。
Broker 扩容时 partition 会均匀分布在新机器。

5. 顺序写为何快

  • Kafka 写入磁盘不是随机写，而是 append-only log
  • Linux 对顺序写进行 预读/预写优化
  • HDD 顺序写 > 随机写 几十倍
  • SSD 也有顺序写优势：更少 FTL 映射冲突

6. PageCache 与 mmap

Kafka 同时使用：

✔ Broker → 磁盘写入：mmap（内存映射）

  • 写 log 文件时，Kafka 使用 FileChannel + mmap
  • 优势：减少一次拷贝（用户态 → 内核态）

✔ Broker → Client 发送：sendfile（真正的零拷贝）

  • 避免将磁盘文件读到用户态发送
  • 网络直接从 PageCache 发出去

📌 结论：

场景 技术
写入磁盘 mmap
发送给消费者 sendfile（零拷贝）

Kafka 二者都用，所以非常快。

三、Zero Copy（零拷贝） & Sendfile

Kafka 的高性能另一个核心：不拷贝数据。

❌ 普通 IO

用户态 ⇄ 内核态 四次 copy

✅ sendfile()

只需一次 copy（DMA → NIC），用户态不参与

零拷贝架构图

效果：

  • 吞吐提升 2～3 倍
  • CPU 使用降低 50%+
  • Kafka 不需要 read() → write()
  • sendfile 让内核直接把 PageCache 内容写入 Socket
  • 数据从未进入用户态内存

四、副本机制：Leader/Follower + ISR

Kafka 每个 partition 有多个副本：

结构：

  • 1 个 leader（读写）
  • N 个 follower（复制 leader）

1. ISR（In-Sync Replicas）

ISR = 所有 跟上 leader 最新进度 的 follower

好处：

  • Leader 切换速度快
  • 不拖慢整体性能
  • 保证数据不丢失

2. 副本同步架构图

五、可靠性：ACK、重试、幂等、事务

1. ACK

acks 含义 是否可能丢消息
0 不等待响应 可能丢
1 Leader 写入即成功 Leader 掉可能丢
all / -1 ISR 全写入才成功 不丢

2. 重试机制完整说明（Producer / Broker）

Producer 的重试：

  • 参数：retries、retry.backoff.ms
  • 如果网络闪断、leader 不可用，则自动重试
  • 若未开启幂等：可能产生重复消息

Broker 的重试（副本同步失败）

  • follower 落后太多会被踢出 ISR
  • leader 写失败会触发：
    • partition leader 重新选举
    • producer 端重新发送

3. 幂等性 Producer（idempotent）

开启后：

Kafka 给每个 producer 分配：

  • PID（唯一标识）

Kafka 给每个 partition 的发送序列号:

  • sequence number（消息序号）

Broker 对每个 (PID, Partition) 维护 last sequence

保证：

  • 重试不会产生重复消息

4.事务（Exactly Once）

Producer 事务包括：

  • beginTransaction
  • send
  • commitTransaction

Kafka 内部写入：

  • 事务记录写入内部日志：__transaction_state
  • Consumer 必须使用 read_committed 才能屏蔽未提交消息

两阶段提交（2PC）+ 幂等 + 内部事务日志 是 Kafka 实现 EOS 的根本。

  • 从 PageCache 读取数据
  • offset 保存在 __consumer_offsets
  • Rebalance 触发条件补充：
    • group 成员变化
    • topic partition 扩容
    • consumer 长时间无法心跳

七、顺序投递问题与解决方案

Kafka 只有：

  • 单 partition 内保证顺序
  • 多 partition 不保证顺序

解决：

  • 同 key 同 partition（如 userId）
  • 只使用一个 partition（牺牲吞吐）
  • Flink/Kafka Streams 做窗口重排序

八、错误处理机制

1. 消息重复

原因：重试
解决：幂等 + 业务幂等（唯一索引/Redis）

2. 消息丢失

原因：acks=1、ISR 小
解决：acks=all + min.insync.replicas≥2

3. 消费阻塞

原因：

  • 消费速度 < 生产速度
  • 大批量消息反序列化耗时
  • 单 partition 的 consumer 处理过慢（无法并行）
  • Rebalance 频繁导致阻塞

解决：

  • 增加 partition（提高并行）
  • 调大 max.poll.interval.ms
  • 使用异步批处理

九、Kafka 3.x：KRaft 架构（无 Zookeeper）

Kafka 3.x 开始：

  • 不需要 Zookeeper
  • 使用 Raft 算法
  • 存储元数据于内部 topic __cluster_metadata
