Kafka的可靠性设计

一、Kafka 的可靠性设计（Exactly once 的基础）

Kafka 的可靠性由 Broker、Producer、Consumer 三侧共同保证。

1. Broker（服务端）可靠性设计

1）多副本机制（Replication）

每个 Partition 有：

  • Leader（负责读写）
  • Follower（同步 Leader 数据）

Follower 通过 pull 方式 拉取 log，确保日志一致。

2）ISR 机制（In-Sync Replicas）

Kafka 把“同步速度跟得上 Leader 的副本”放进 ISR。

只有 ISR 中的副本才算可靠：

  • Leader 写成功后必须同步给 ISR 中全部副本
  • ISR 中多数派保存了数据 → 允许 Leader 崩溃后快速切换

3）ACK 机制（acks 配置）

acks 含义 可靠性
0 不等待 Broker 回执 最差
1 Leader 写本地日志即返回 可丢数据
all / -1 ISR 全部写入成功才返回 最高可靠性

2. Producer（生产端）可靠性

1）重试机制（retries）

Producer 失败会自动重试（网络抖动时常见）。

2）幂等性（Idempotence）

通过 Producer ID（PID）+ Sequence Number 实现，保证“同一消息的重试不会造成重复数据”。

3）事务（Transaction）

配合幂等写，实现：

Exactly Once 语义（EOS）

3. Consumer（消费端）可靠性

1）手动提交 offset

Kafka offset 放在 Broker 上，由 consumer 自己决定何时提交。

常见方式：

  • 消费成功 → 手动 commit
  • 消费异常 → 不 commit，下次继续处理

2）幂等消费

服务端必须要有去重机制（如“订单号 + 幂等表”）。

3）事务性消费（Kafka Stream 或事务消费者）

使用 Kafka 的事务 API：

  • 读取事务性 partition
  • 只消费 committed 数据
  • 实现 Exactly Once 消费

二、Kafka 的幂等性设计（Idempotence）

Kafka Producer 的幂等性设计用一句话概括：

PID + SequenceNumber → Broker 端避免重复写入，从而实现“对同一条消息的重试不会造成重复”

  • retries=Integer.MAX_VALUE

4. 幂等性不能解决的问题

Kafka 幂等性不是万能的，它不能解决跨分区、跨主题的事务一致性问题。

例如：

  • 同一批消息分别写入多个 partition
  • 或写入多个 topic

这些需要 Kafka 的事务 API（事务性 producer）。
