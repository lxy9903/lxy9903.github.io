Kafka VS RabbitMQ

一、Kafka vs MQ 的核心区别（本质差异）

Kafka 是“分区日志（Partition Log）系统”

传统 MQ（RabbitMQ / RocketMQ）是典型的 队列模型（Queue）。

特性 Kafka RabbitMQ / RocketMQ 等 MQ
存储结构 分区日志（append-only log） 队列
消费方式 消费者自己维护 offset MQ 维护 ack/offset
高并发能力 极高（靠分区） 较强 / 中等
顺序性 每分区强顺序 队列天然保持顺序
延迟 可做到 < 5ms 因路由 / broker 处理较高
扩展性 水平扩展更容易 需要多队列、多 exchange

二、为什么 MQ 能保证顺序性？

1）Kafka 为什么能保证顺序？

因为 Kafka 的单个 Partition 是 append-only 的日志文件：

  • 同一 Partition 内的消息按写入顺序追加（单线程写入）
  • 消费时也按 offset 顺序读取
  • 所以 Partition 内天然保持强顺序性

但多分区就无法保证全局顺序

2）RabbitMQ / RocketMQ 为什么能保证顺序？

它们的设计是传统“队列”模型：

  1. 对同一个 Queue，消息都是 FIFO
  2. 使用单个 consumer 或消费端按顺序 ack
  3. Queue 本身就是一个单链表/双端队列结构

只要：

  • 生产端按顺序发送
  • 不使用多消费者并行消费

那顺序就是天然的。

3. MQ 中如何保证顺序？

RabbitMQ / RocketMQ：

关键设计：

  1. 一个 Queue 只被一个 Consumer 消费
  2. 消费端不要并发处理同一个 Queue
  3. Producer 不要异步乱序发送（同一个 key 必须串行发送）

RocketMQ：

👉 同一个 orderId 总是发送到同一个 MessageQueue（同一个 broker queue）
👉 从而保证顺序

四、为什么顺序会被破坏？

Kafka 乱序常见原因：

  1. 多分区（orderId 不落同分区）
  2. producer 开启并发发送（in-flight > 1）
  3. producer 重试导致消息插队
  4. consumer 并发消费

RabbitMQ / RocketMQ 乱序原因：

  1. 多 consumer 并发同 queue
  2. broker 内的 requeue / nack 导致消息重新排队
  3. 多 queue，却没有保证同 key 的路由策略

五、最终如何在项目里保证顺序性

同一业务 Key（如订单号、用户 ID）始终映射到同一个队列 / 分区，生产端串行发送，消费端单线程按顺序消费，保证提交和处理逻辑是幂等的。

简述如下：

  • 生产端保证同 Key 分区 / 队列一致性
  • 生产端保证顺序发送（in-flight=1，幂等开启）
  • 队列维度只用单消费者（或业务 Key 分片消费）
  • 消费端处理幂等，防止重试打乱顺序

六、用一句话总结

Kafka 的顺序性依赖 Partition；MQ 的顺序性依赖 Queue。要实现顺序性，核心是确保同一业务 Key 落到同一 Partition/Queue，并保持发送端和消费端的串行化，加上幂等避免重试乱序。
