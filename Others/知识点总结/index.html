一、知识点总结

1. Java / 运行时与框架

1.1 反射（Reflection）

  • 是什么：Java 运行时检查/操作类的方法、字段、构造器、注解的能力（Class, Method, Field, Constructor）。
  • 原理：编译期产生 .class（字节码） -> JVM 装载类 -> Class 对象代表类元数据。反射 API 操作 Class 对象并通过 MethodHandle / Native 调用实际方法。
  • 常见用法：动态实例化（clazz.newInstance() / getConstructor().newInstance()），访问私有字段 setAccessible(true)，注解处理器运行时读取注解。
  • 代价与风险：慢（方法解析、权限检查），破坏封装（可引发安全问题），JIT 优化受限（反射调用不能内联）。
  • 调优建议：频繁使用时缓存 Method/Field 对象，避免频繁 setAccessible，使用 MethodHandle 或 LambdaMetafactory 提升性能。

1.2 动态代理（JDK / CGLIB）

  • JDK 动态代理：基于接口，运行时生成接口的代理类（Proxy.newProxyInstance），通过 InvocationHandler 转发调用。适用于有接口的场景。
  • CGLIB（字节码增强）：对类生成子类来拦截方法（通过 ASM 操作字节码），可代理没有接口的类（但 final 方法/类无法代理）。Spring 在没有接口时使用 CGLIB。
  • 实现要点：代理类在调用时插入横切逻辑（日志、事务、权限等），并决定是否调用 super/原方法。
  • 坑：多次代理可能导致代理链变深；序列化问题；使用 CGLIB 需注意构造器调用和类加载器。
  • 性能：JDK 代理较轻，CGLIB 在初次生成类有开销，但之后性能接近直接调用；对于超高频调用推荐 bytecode 预生成或 ASM 优化。

1.3 AOP（原理 & Spring AOP）

  • 概念：面向切面编程，通过切面 (Aspect)、通知 (Advice)、连接点 (JoinPoint)、切点 (Pointcut) 把横切关注点从业务逻辑抽离。
  • Spring AOP：默认基于代理（JDK 或 CGLIB）。基于 BeanPostProcessor 在 bean 创建时包装代理。
  • 流程：
    • 解析切面注解/配置 -> 生成 Advisor（Pointcut + Advice） -> 在 BeanFactory 初始化时为匹配的 bean 创建代理 -> 代理在方法调用时按照 advice 顺序执行（环绕、前置、后置、异常等）。
  • 限制：基于代理，只有通过代理对象（通常是外部调用）能触发 AOP；同类内部 this.method() 不触发。AspectJ 的编译时/加载时织入可以绕过此限制。
  • 实现细节：Spring AOP 使用 ProxyFactory、AdvisedSupport、AopProxy 实现，Advice 执行顺序由 Ordered 或 @Order 决定。

1.4 类加载（ClassLoader 机制）

  • 三大类加载器：Bootstrap（由 JVM 本地实现），Platform（或称 Ext），Application（系统类加载器）。自定义类加载器常用于隔离/热更新。
  • 双亲委派模型：加载请求优先委派给父加载器，防止重复加载核心类和提升安全性。自定义类加载器可选择打破委派（如插件系统）。
  • 类的生命周期：加载 -> 验证 -> 准备（静态变量分配）-> 解析（符号引用转为直接引用）-> 初始化（执行静态初始化块）。
  • 热替换/热部署要点：同一个类名、同一类加载器下不能卸载类；要实现热替换需使用新的类加载器加载新版本并释放旧类加载器引用以便 GC 回收。

1.5 Spring Boot 启动流程（简要但关键步骤）

  • SpringApplication.run(...)
    • 创建 SpringApplication 实例，准备环境（Environment）和 ApplicationContext 类型选择（AnnotationConfigServletWebServerApplicationContext 等）。
    • SpringApplication 调用 prepareEnvironment()、createApplicationContext()。
    • 加载 ApplicationContext -> 注册 BeanFactory 后处理器（BeanFactoryPostProcessor），如 ConfigurationClassPostProcessor（负责处理 @Configuration、@Bean、@ComponentScan）。
    • 执行 refresh()：BeanDefinition 注册 -> BeanFactoryPostProcessor -> BeanPostProcessor 注册 -> 单例 Bean 实例化（按照依赖）、@Autowired 注入、@PostConstruct 执行。
    • ApplicationReadyEvent 发布。
  • 调优关键点：减少自动配置扫描范围（spring.factories / spring.autoconfigure）、惰性初始化（spring.main.lazy-initialization=true）、按需禁用不必要的 auto-config。

1.6 JVM 垃圾回收（具体回收算法与细节）

  • 堆代划分：Young（Eden + S0/S1）、Old（Tenured）、Metaspace（类元空间，JDK8+）。
  • 主要收集器（选择依据 JVM 版本、低延迟或高吞吐）：
    • Serial（单线程，适合客户端）
    • Parallel / Parallel Old（吞吐量优先）
    • CMS（Concurrent Mark-Sweep，低停顿，已过时）
    • G1（分区并行，目标停顿时间，JDK 默认适用大多数应用）
    • ZGC / Shenandoah（低暂停，支持超大堆，暂停时间极短）
  • 算法要点：
    • 复制（Copying）：用于年轻代，Eden->Survivor 复制；优点：分配/回收快；缺点：需要额外空间。
    • 标记-清除（Mark-Sweep）：标记可达对象，清除不可达；缺点：会产生碎片。
    • 标记-整理（Mark-Compact）：标记后整理，消除碎片但代价较高。
  • 主要触发条件：Eden 空间不足触发 Minor GC（复制/晋升），Old 空间不足或触发条件时触发 Full GC（老年代回收，可能标记-整理或并发标记）。
  • 调优点：调整年轻代/老年代比例，跟踪晋升速率和晋升失败，减少 Full GC，使用 -XX:+PrintGCDetails + GC 日志分析；若需要低停顿，优先考虑 G1/ZGC。
  • 实际面试看点：对象分配（逃逸分析决定是否在栈上分配）、对象晋升阈值（MaxTenuringThreshold）、分代大小比对吞吐和停顿的影响。

1.7 类型擦除（Type Erasure）

  • 概念：Java 泛型在编译时用于类型检查，但在运行时泛型信息被擦掉，生成的字节码使用原始类型（Raw Type）。

    • 编译器插入必要的强制类型转换 (cast)
    • 运行时 JVM 不保留泛型类型信息

1.8 泛型（Generics）

  • 概念：Java 泛型允许在编译期对类型进行参数化，使集合和方法能安全处理指定类型。
  • 关键特性：
    • 编译期类型安全
    • 自动类型转换
    • 类型擦除实现，运行时无泛型信息
  • 示例：
  • 类型边界：
    • T extends Number → 编译后 T 被擦除为 Number
  • 面试点：

    • 类型擦除与桥方法（Bridge Method）
    • 通配符 ? 和协变/逆变

1.9 编译与运行（Compile vs Run）

  • 编译（Compile）：
    • 将源码 .java 转换成字节码 .class

    • JVM 加载字节码、分配内存、执行指令
    • 方法调用时多态（动态绑定）
    • 运行时处理异常（运行时异常、Error）

  • 面试点：
    • 泛型在编译期类型擦除，运行期只看到 Object
    • 多态：编译期检查方法签名，运行期根据对象类型动态绑定

1.10异常（Exception）

  • 分类：
    • Checked Exception（编译时异常）：
      • 继承 Exception 但不继承 RuntimeException
      • 必须 try-catch 或在方法上 throws 声明
      • 示例：IOException, SQLException
    • Unchecked Exception（运行时异常）：
      • 继承 RuntimeException
      • 可选捕获或声明
      • 示例：NullPointerException, IndexOutOfBoundsException
    • Error（严重错误）：
      • 继承 Error，一般不可捕获
      • 示例：OutOfMemoryError, StackOverflowError
  • 编译期 vs 运行期：
    • Checked Exception → 编译期强制检查
    • Unchecked / Error → 运行期抛出
  • 面试点：
    • 区分 Checked 与 Unchecked Exception
    • 运行期异常常因逻辑错误，可修复而不是捕获
    • 编译期异常主要用于可恢复的外部操作

2. 存储与数据库

2.1 B+ 树（结构、时间复杂度、层数）

  • 结构：B+ 树所有值都在叶子节点，内节点仅用于索引（key + child pointer），叶子节点通过链指针相连（便于范围查询）。内外节点通常以页（page）为单位（磁盘/内存页）。
  • 时间复杂度：查找、插入、删除都为 O(log_f N)（f = 分支因子 / 每个内节点最多指向的子节点数），通常视为 O(log N)。
  • 层数计算示例（实际面试常问）：
    • 假设页大小 4KB（4096B），每个索引项（key + pointer）约 16B（key 8B + pointer 8B，视具体实现而定），则每个内节点最大孩子数 f ≈ 4096 / 16 = 256。
    • 对于 N = 10,000,000（千万级） 条记录，树高度 h 满足 f^h >= N。令 f=256：
      • h = ceil(log_{256}(10,000,000)) = 3。
      • 也就是说：root（1）→ level1（256）→ leaves（256^2 ≈ 65536 节点，足以覆盖千万条）——实际高度通常为 3 ~ 4 层，非常浅，读磁盘的随机 I/O 不多。
    • 对于 N = 1,000,000,000（10 亿），h = ceil(log_{256}(1e9)) ≈ 4。
  • 要点：索引高度很低 → 单次索引查找涉及的磁盘页访问少（通常 3~4 次），所以 B+ 树对大规模数据的随机查找是高效的。
  • 维护开销：插入/删除可能导致节点分裂/合并，需要更新父节点，写放大（尤其在磁盘上），因此批量插入可通过排序后顺序写优化。

2.2 MySQL 插入流程（典型 InnoDB 行为）

  • 客户端到服务器：客户端通过 Connector（驱动）发送 SQL -> MySQL Server（sql_parse） -> 查询解析（解析器/语法树）-> 优化器生成执行计划 -> 执行引擎。
  • InnoDB 插入（事务、行写入）关键步骤：
    1. 获取必要的锁（行锁或 gap lock，视隔离级别与语句类型）。
    2. 插入记录到 InnoDB Buffer Pool（内存页）。
    3. 生成 Undo log（用于事务回滚/MVCC），并写入内存中的 undo 区。
    4. 生成 Redo log（重做日志）记录到 InnoDB 的 redo log buffer（内存）。
    5. 如果 innodb_flush_log_at_trx_commit = 1：commit 时将 redo log flush 到磁盘（保证持久性）；若为 2 或 0 则可能会延迟。
    6. 数据页脏（dirty page）将在稍后被后台线程刷写到磁盘（Checkpoint、Doublewrite Buffer 机制避免半写问题）。
    7. 如果开启 binlog（binlog_format = ROW）并且 sync_binlog 配置要求，binlog 的写与刷新会涉及时序（通常在事务提交点记录 binlog，以便主从复制）。
  • 注意顺序（非常重要，面试常问）：
    • 事务提交的持久性依赖 redo log 的 flush（+ binlog 的 flush 顺序）。典型安全配置：先写 binlog（可能 flush），再写 redo log，再 commit（或主/从复制要求）。
  • 性能热点：避免频繁小事务（commit 成本高），使用批量插入，调整 innodb_flush_log_at_trx_commit 与 sync_binlog 根据容错要求权衡性能/持久性。

2.3 千万数据库 LIMIT 与分页

  • 问题：SELECT ... LIMIT offset, size 当 offset 很大时，数据库需要跳过 offset 条记录（或遍历索引），时间复杂度随 offset 线性增长，性能极差。
  • 替代方案：
    • Keyset Pagination（基于游标/索引）：WHERE (id > last_seen_id) ORDER BY id LIMIT size —— 使用索引，性能稳定。
    • 倒排/覆盖索引：只返回索引列（避免回表）以减少 IO。
    • 预计算/分区：按时间/范围分区，分页只在某个分区内执行。
    • Seek 方法：用索引定位开始点（索引扫描而非 OFFSET 跳过）。
  • 千万级场景：若真的需要任意页随机访问，设计上应避免 OFFSET，或采用外部分页（缓存页面、基于 user-friendly cursor、或专门的分页服务）。

2.4 锁相关、并发（MySQL）

  • 锁类型：
    • 表级锁（MyISAM） vs 行级锁（InnoDB）
    • InnoDB 行级锁细分：共享锁 (S)、排他锁 (X)、意向锁 (IS/IX)、Gap Lock / Next-Key Lock（防止幻读）。
  • MVCC（多版本并发控制）：读不加锁（快照读），通过 undo log 和事务版本号（trx id）实现可重复读 / 快照隔离。
  • 死锁检测：InnoDB 会维护等待图并自动检测死锁，选择受影响最小事务回滚。面试常问如何分析死锁（查看 SHOW ENGINE INNODB STATUS）。
  • 乐观锁 vs 悲观锁：
    • 悲观锁：依赖数据库锁（行锁）——适用于写冲突高场景。
    • 乐观锁：在应用层用版本号（version）或 compare-and-set（WHERE version = ?） —— 适用于冲突少的高并发场景。
  • 并发控制技巧：尽量缩短事务时间、合理拆分事务、避免长事务导致 undo log 膨胀与阻塞 purge。

3. 分布式消息与系统设计

3.1 RabbitMQ（AMQP）数据流 & 多节点

  • 核心概念：Producer -> Exchange（direct/fanout/topic/headers）-> Queue -> Consumer。RoutingKey & Binding 决定消息如何分发到队列。
  • 确认机制：Publisher Confirm（确认消息被 broker 接收），Consumer Ack（消费端确认消息已处理）。
  • 集群/镜像队列：
    • 普通集群：节点共享元数据，但队列通常在某一节点上（队列主节点），消费者与生产者连接到任意节点，若非主节点则通过网络转发到主节点，可能有跨节点流量。
    • 镜像队列（classic mirrored queues / quorum queues）：复制队列内容到其他节点以提高可用性（quorum queues 更推荐用于持久化与高可用）。
  • 多节点发送/消费要点：
    • Producer 可连接任意 Broker 节点；消息路由后最终写入队列所在节点。
    • Consumer 订阅队列，并由队列所在节点推送消息（如果消费者连接的不是队列所在节点，会通过内部网络转发）。
    • 在高并发场景要考虑网络带宽、队列主节点的负载与流量热点。
  • 常见坑：默认瞬时队列不持久化、消息丢失与 ack 配置（autoAck=false + 手动 ack 为可靠），镜像队列延迟、leader 选举开销。

3.2 Kafka 数据流 & 多节点（重点）

  • **核心概念 **：Producer -> Topic -> Partition -> Replica（分片与副本），Consumer Group 负责消费分区。
  • Partition：消息的并行单元，写入同一 partition 保证顺序。分区数量决定并行度。
  • Replica 与 ISR：每个 partition 有 Leader（负责读写）和若干 Follower（复制）。ISR（In-Sync Replicas）表示与 Leader 同步的副本集合。只有 ISR 内的副本才能成为 leader。
  • 写流程（Producer）：
    • Producer 根据 partitioner（key 或轮询）选择 partition -> 将消息写到 leader（请求可设置 acks=0/1/all）。
    • 若 acks=all 则 Leader 等待 ISR 内所有副本的复制确认（或至少写入本地日志），以保证更高耐久性。
  • 读流程（Consumer）：
    • Consumer Group 中每个 partition 被一个 consumer 实例消费（实现水平扩展且保证每 partition 的顺序性）。
    • Offset 存储：可存储在 Kafka 内部（__consumer_offsets）或外部（ZK 在旧版本），consumer 可选择自动提交或手动提交 offset。
  • 多节点要点：
    • Producer 可连接任意 broker，broker 将被转发到 partition leader。如果 leader 转移，producer 会自动重试与更新元数据。
    • Broker 集群通过 ZooKeeper（旧版本）或自身集群元数据（KRaft，新版本）协调 leader 与元数据。
  • 吞吐与延迟调优：批量发送（linger.ms, batch.size）、压缩、适当的副本数和 ISR 策略、磁盘顺序写（segment 文件）。
  • 常见坑：分区数设计（上线后改分区复杂）、消息过大（>1MB 默认为 max.message.bytes）、保证 exactly-once semantics (EOS) 需要事务 API，消费幂等性设计。

3.3 分布式锁（实现、RedLock）

  • 常见实现：
    • 基于数据库：通过 SELECT ... FOR UPDATE 或 INSERT ... + 唯一索引实现（慢，需注意事务保持时长）。
    • 基于 Redis：SET resource_name token NX PX ttl（SET NX + expire 原子）。消费端成功拿到 lock 后通过比对 token 来释放（防止误释放）。
    • RedLock（分布式 Redis 多节点算法）：在多个 Redis 实例上尝试加锁并在多数实例上获得锁才认为获取成功，以降低单点故障概率。存在争议（是否在异步网络情况下依然安全）。
  • 边界条件：锁失效（客户端长执行需要续期）、网络分区（split-brain）、锁重入与可重入性、锁释放竞争（使用 token 校验）。
  • 建议：简单场景用单节点 Redis 加上合理 ttl 和 watch/renew；高级场景评估使用 ZooKeeper/etcd（提供强一致性的 leader election primitive）。

3.4 分布式事务（2PC、TCC、Saga）

  • 2PC（Two-Phase Commit）：
    • 协议：Coordinator 发 prepare -> 各参与方本地执行并保持未提交状态 -> 返回 yes/no -> Coordinator decide commit/abort -> broadcast commit/abort -> 各方 apply/rollback。
    • 优点：强一致性（原子性）。缺点：阻塞（若 coordinator 挂掉，参与者可能长期锁资源）、性能开销高，复杂恢复流程。
  • TCC（Try-Confirm-Cancel）：
    • 三步：Try（资源预留） -> Confirm（确认并真正提交）/Cancel（释放预留）。用于业务可明确预留/释放的场景（库存预占、订单等）。
    • 优点：较清晰业务语义，非阻塞（若实现得当）。缺点：实现复杂（每个操作需实现三套接口），幂等/补偿复杂。
  • Saga（补偿事务）：
    • 将大事务拆分为一系列子事务，每个子事务都有补偿动作。通过编排方式（orchestration）或事件驱动（choreography）实现最终一致性。
    • 优点：可伸缩、无全局锁，适合长事务。缺点：补偿动作需设计，可能存在中间态窗口期。
  • 如何选：强一致且短事务可考虑 2PC；跨组织或长事务、可接受最终一致性时用 Saga；TCC 在需要明确预占资源且可实现 confirm/cancel 时效果好。

4. 网络与 IO

4.1 HTTP / HTTPS 流程（关键步骤）

  • HTTP 基本流程：
    • TCP 三次握手（SYN, SYN-ACK, ACK）建立连接。
    • 客户端发送 HTTP 请求（请求行、Header、Body）。
    • 服务器处理请求并返回响应（状态码、Header、Body）。
    • 若使用 Keep-Alive，连接保持可复用，否则四次挥手关闭。
  • HTTPS（TLS）增加的步骤：
    • TLS 握手（ClientHello -> ServerHello + Cert -> ClientKeyExchange -> Finished），包括公钥交换（RSA 或 ECDHE）和对称密钥协商。
    • 验证证书链（从服务器证书到受信任 CA），校验有效期、域名。
    • 握手完成后基于对称密钥加密后续 HTTP 消息。
    • 优化：会话复用 / session resumption（Session ID / Session Ticket）和 TLS 1.3 的 0-RTT（有风险）。
  • 要点：证书链、信任根、密钥协商方式（影响前向保密），加密套件选择对性能和安全性的影响。

4.2 NIO（Non-blocking IO）

  • 核心类：Selector、SelectableChannel（SocketChannel）、ByteBuffer。
  • 模型：一个或少量线程运行 Selector，监听多个 Channel 的事件（OP_ACCEPT, OP_READ, OP_WRITE）。适合大量连接/低并发每连接处理少量数据的场景（如高并发网络服务）。
  • 线程模型建议：通常 Boss（accept）线程 + N 个 Worker（处理读写与业务逻辑）或 Reactor 模式。注意避免在 IO 线程做重 CPU/阻塞操作（应交给线程池）。
  • 常见坑：ByteBuffer 的使用要注意 flip/clear/compact；直接缓冲区（DirectBuffer）对 GC 影响较小但分配开销高；selector.select() 需要处理返回 0 情形与空轮询（wakeup/bugs）。

4.3 零拷贝（Zero-Copy）

  • 目标：减少数据在用户态与内核态间的复制次数，降低 CPU 与内存带宽消耗。
  • 实现方式：
    • **sendfile()**：从文件直接发往 socket，数据无需拷贝到用户态。
    • **mmap()**：将文件映射到用户空间，内核页直接共享。
    • splice()/tee（Linux）：在内核内将数据从一个 fd 移动到另一个 fd，不经过用户态。
  • 适用场景：大文件传输（静态资源服务）、高吞吐场景。
  • 注意：有些场景（小消息、需拷贝变换）仍需拷贝；零拷贝并非银弹（受限于内核实现与网络驱动）。

5. 可用性 / 分布式理论 / 降级策略

5.1 CAP 理论（与常见中间件分析）

  • CAP 三要素：Consistency（一致性）、Availability（可用性）、Partition tolerance（分区容忍性）。在有网络分区时，系统只能在 C 与 A 间取其一。
  • 中间件定位举例（高层次）：
    • Zookeeper / etcd：优先 C（强一致性），在分区发生时倾向牺牲可用性来保证一致性（CP）。
    • Kafka：在默认副本策略下偏向 AP（在某些配置/ISR 策略下折中），但可调成更强一致性（设置 min.insync.replicas）。
    • Cassandra / DynamoDB：偏向 AP（可配合读写修复实现最终一致性）。
    • Redis（单节点）：在主从及哨兵模式下可配置性高；原生单节点为 A，复制场景取决于复制策略（可能牺牲一致性）。
  • 要点：设计时先确定业务对一致性 vs 可用性的需求，选合适中间件与配置（例如 Kafka 的 acks、Cassandra 的 consistency level）。

5.2 熔断方案（策略 + 实现）

  • 目的：当下游不可用或响应慢时通过熔断避免雪崩，快速失败，保护服务并触发降级/扩容。
  • 基本状态机：CLOSED（正常） -> OPEN（断开，拒绝请求） -> HALF-OPEN（探测恢复） -> CLOSED。
  • 判断依据 / 触发条件：错误率阈值（如 50%）、响应时间阈值、连续失败次数、并发排队长度。
  • 实现要点：
    • 滑动窗口（计数器或环形缓冲）统计失败率与成功率；
    • 短路：在 OPEN 状态直接返回 fallback；
    • 探测策略：定时放通少量请求或按指数退避；
    • 配套措施：降级策略（返回缓存值或默认值）、限流（令牌桶/漏桶）、隔离（线程池/信号量）。
  • 常见实现：Resilience4j、Sentinel、Hystrix（已停更但概念仍常被引用）。
  • 实际注意：熔断阈值和恢复策略必须根据业务特性调优，误触可能导致可用性下降。

6. 监控 / 并发与运维

6.1 监控要点（Metrics / Tracing / Logs）

  • 三柱：Metrics（Prometheus）、Tracing（OpenTelemetry / Jaeger）、Logging（集中式 ELK / Loki）。
  • 关键指标：
    • 应用层：请求率 RPS、错误率、P99/P95 响应时间、垃圾回收次数/耗时、线程池队列/活跃数。
    • 基础设施：CPU、内存、磁盘 IO、网络带宽、文件句柄、进程耗时。
    • 业务指标（SLO）：交易成功率、延迟、系统吞吐量。
  • 告警与 SLO：设置合理阈值并联动 runbook（故障处理步骤），避免告警疲劳。分级告警（警告 vs 致命）。

6.2 并发数据结构/原理

  • CAS（Compare-And-Swap）：无锁原语，适用于乐观并发；要注意 ABA 问题（可借助版本号/Tagged pointers 解决）。
  • 线程池配置要点：corePoolSize、maximumPoolSize、队列类型（SynchronousQueue / LinkedBlockingQueue / ArrayBlockingQueue）、拒绝策略。
  • 常见并发优化：局部性、减少锁粒度、读写分离、使用并发集合（ConcurrentHashMap 分段/桶策略）。

7. 并发相关

7.1 Java 内存模型（JMM）

关键概念：

  • 可见性：volatile、synchronized、final 语义
  • 有序性：指令重排、happens-before 规则
  • 原子性：基本类型、CAS

7.2 CAS（Compare-And-Swap）

底层：

  • CPU 原子指令：cmpxchg
  • 失败自旋，可能产生 ABA 问题（AtomicStampedReference / 版本号解决）

用途：

  • 原子类、AQS、并发容器、分段锁

7.3 AQS（AbstractQueuedSynchronizer）

核心：

  • state(int 状态位)
  • CLH 双向阻塞队列
  • exclusive/shared 两种模式

典型使用：

  • ReentrantLock、CountDownLatch、Semaphore、ReentrantReadWriteLock

7.4 线程池 ThreadPoolExecutor

关键参数：

  • core/min/max
  • 队列（SynchronousQueue / LinkedBlockingQueue / ArrayBlockingQueue）
  • 拒绝策略（4 种）

常问点：

  • 为何不要设置无限队列？
    → 任务堆积导致 OOM，最大线程数永远无法扩展
  • IO 密集型池大小？
    → CPU 核 * 2 或更高（要看阻塞时长）

7.5 False Sharing（伪共享）

CPU Cache Line（通常 64 bytes）内多个线程修改相邻变量导致频繁同步失效 → 性能大幅退化。

解决：

  • @Contended
  • 手动 padding

7.6 Copy-On-Write（COW）

典型：CopyOnWriteArrayList
适用：读多写少
缺陷：写放大、内存翻倍、可能读到旧数据（弱一致性）

7.7 并发集合

  • ConcurrentHashMap（CAS + 分段锁 → 1.8 变成 Node+CAS+链表树化）
  • ConcurrentLinkedQueue（无锁队列）
  • BlockingQueue（多线程生产/消费）

7.8 synchronized 与 ReentrantLock

区别：

  1. synchronized JVM 层 → 自动释放锁
  2. ReentrantLock 代码层 → 可中断、可限时、公平锁、条件锁

JVM 优化：

  • 偏向锁（线程独占倾向）
  • 轻量级锁（CAS）
  • 重量级锁（monitor）
  • 锁膨胀、锁消除、锁粗化

7.9 ThreadLocal

用途：线程隔离变量，比如 traceId、连接、上下文
危害：线程池 + 未 remove → 内存泄漏（老对象长期存留）

16. 微服务治理

16.1 服务雪崩与解决方案（舱壁隔离 / 过载保护）

服务雪崩＝一个下游服务变慢 → 大量请求堆积 → 线程耗尽 → 导致更多服务超时 → 形成级联故障。
本质：资源被耗尽（线程、连接、CPU）。

工程解决方案

问题 解法 原因
线程被占满 线程池隔离（舱壁） 防止 A 服务把整个系统拖死
请求堆积 请求超时 + 快速失败 不等待必失败的请求
过载 自适应过载保护（拒绝 + 降级） 平滑保护系统
流量突增 限流（Token Bucket / 滑动窗口） 防止瞬时打爆
依赖不稳定 熔断 假死服务不再被反复调用

舱壁隔离的落地方式

  • 线程池隔离（每个服务一套线程池）
  • 信号量隔离（限制最大并发）
  • 流量隔离（不同业务 key 不同 QPS）

16.2 熔断器原理（Hystrix / Sentinel）

熔断＝检测目标服务失败率/响应时间 → 达到阈值后“短路”调用，直接失败或走 fallback。
核心是：避免反复访问已故障的依赖。

Hystrix 熔断原理（经典三态机）

  • Closed：正常状态，记录失败率
  • Open：失败率超过阈值 → 熔断，快速失败
  • Half-Open：尝试少量请求，看服务是否恢复

Sentinel 熔断（比 Hystrix 更强）

Sentinel 的熔断触发方式有三种：

  1. 慢调用比例
  2. 异常比例
  3. 异常数

Sentinel 最大区别：
✔ 基于滑动窗口统计（比 Hystrix 更精准）
✔ 单机限流 + 集群限流（Hystrix 做不到）
✔ 动态规则（改配置无需重启）

16.3 API 限流算法（漏桶、令牌桶、滑动窗口）

限流算法 特点 适合场景
漏桶 Leaky Bucket 出水速率恒定 平滑流入流量（直播/接口稳定）
令牌桶 Token Bucket 可突发（允许积累令牌） 正式生产最常用（如 Gateway/Sentinel）
滑动窗口 Sliding Window 精准统计 QPS 精准限流（如 Sentinel）
  • 漏桶只保证输出平滑，不允许突发。
  • 令牌桶允许突发，是 Nginx、Envoy、Sentinel 默认模型。
  • 滑动窗口不用于发令牌，而用于 统计实时 QPS。

16.4 配置中心推模式与拉模式

拉模式（pull）

  • 服务启动主动从配置中心拉取配置
  • 配置变更依赖轮询或主动 refresh
  • 注意：延迟高，不适合配置频繁变更

推模式（push）

  • 配置中心使用 长轮询 + 版本号 推送变更
    • Apollo：短轮询 + 长轮询混合
    • Nacos：长轮询（/v1/cs/configs/listen）
模式 优点 缺点
拉模式 简单稳定 实时性弱，依赖轮询
推模式 实时、低延迟 服务端压力大（长轮询）

16.5 链路跟踪（Trace / Span）原理

  • TraceId：一次请求的全局唯一 ID（贯穿整个链路）
  • SpanId：链路中的一个执行节点
  • parentSpanId：父节点标记
  • 上下游传递：HTTP Header（如 traceparent）

为什么要做链路追踪

  • 定位慢调用
  • 分析跨服务异常
  • QPS、端到端延迟、依赖拓扑

实现原理（OpenTelemetry/Jaeger）

  • 入口生成 TraceId（或复用上游）
  • 每个调用创建 Span
  • Span 中记录：
    • 耗时
    • 标签（tag）
    • 日志（log）
    • 事件（event）
  • 数据通过 agent/exporter 落地（OTLP、Kafka、Collector）

关键点：采样策略

  • 全采样（低流量）
  • 固定比例采样
  • 自适应采样（推荐，动态调节保留比例）

二、重点计算示例（B+ 树层数的数字演示）

（为面试时能口算/写出逻辑）

  • 假设页大小 4KB = 4096 bytes，索引键 + 指针 = 16 bytes → fanout f = 4096 / 16 = 256。
  • 需要覆盖的记录 N = 10,000,000（1e7）
    • 求最小高度 h，使得 256^h >= 10,000,000。
    • log_{256}(10,000,000) = log(10,000,000) / log(256)。约计算得 h ≈ 2.7 → ceil 得 h = 3。
  • 解释：高度 3 表示从 root 到 leaf 只有 3 层磁盘页访问，说明 B+ 树在千万级上仍非常扁平，查询磁盘 IO 次数少。
