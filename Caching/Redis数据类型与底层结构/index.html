Redis数据类型与底层结构

数据类型与底层结构 — 详解

1) String（底层：SDS — Simple Dynamic String）

内部实现（SDS）

  • SDS 不是 C 的 char*，它在内存前方保存长度/分配容量信息（避免 strlen），并允许二进制数据（包含 \0）。
  • 变种：embstr（短字符串优化）和 raw（标准分配）。
    • embstr：当字符串很短时，键和值会一起做一次小内存分配（节省指针与碎片）。
    • raw：普通字符串开销略大但灵活。

复杂度

  • GET/SET：O(1)
  • CONCAT / APPEND：amortized O(1)（SDS 会扩容）
  • strlen：O(1)（因为 SDS 存储长度）

常见命令

  • GET, SET, INCR, APPEND, STRLEN, MGET, MSET

使用建议 / 坑

  • 大字符串会占用大量内存，避免把超大二进制对象当 String 存储（比如视频、整个 JSON）。
  • 对频繁变化的字符串，SDS 扩容策略会导致内存抖动，关注内存增长。

2) List（底层：quicklist）

quicklist 是什么

  • 从 Redis 3.x 起，List 采用 quicklist：它把多个压缩的 ziplist 节点链接成双向链表（每个节点是 ziplist/listpack）。
  • 设计初衷：同时兼顾内存效率（ziplist）和快速的头尾操作（linked list 特性）。

内部结构

  • quicklist 节点：每个节点包含一个 ziplist（紧凑存储若干元素）。
  • 节点之间双向链表，便于 O(1) 的头尾插入/删除。
  • 节点内使用压缩（listpack），减少内存。

复杂度

  • LPUSH / RPUSH / LPOP / RPOP：O(1)
  • LINDEX：O(N)（需遍历，若索引靠近头或尾则快）
  • LINSERT：O(N)（需要查找）
  • LRANGE：O(N)（遍历范围）

常用命令

  • LPUSH, RPUSH, LPOP, RPOP, LINDEX, LRANGE, BLPOP, BRPOP

使用建议 / 坑

  • 用作消息队列/任务队列非常普遍，但注意单个 list 的过长会导致遍历命令（如 LRANGE 大范围）阻塞。
  • 使用阻塞命令（BLPOP）时注意多个消费者竞争同 list 导致热点。
  • big-list：拆分成多个 list 或使用 stream。

3) Hash（底层：ziplist / hashtable）

编码切换

  • 小 hash（字段数量少且 field/value 都短）使用 ziplist（compact array-like）或 listpack（新），节省内存。
  • 达到阈值后（配置参数），切换到 hashtable（O(1) 访问）。

内部实现

  • ziplist：连续内存存储的序列，每个 entry 存储前一项长度与 data（节省指针）。
  • hashtable：为大量 field 提供 O(1) 查找。

复杂度

  • HGET/HSET/HDEL：O(1)（hashtable），ziplist 下 HGET 是 O(N)（扫描）

常用命令

  • HSET, HGET, HMSET, HGETALL, HDEL, HEXISTS, HINCRBY

使用建议 / 坑

  • Hash 常用于对象存储（user:100 -> hash of fields），比多个键更节省空间（共享 key 的 overhead）。
  • 使用 HGETALL 在大 hash 上会把大量数据一次性拉出，注意内存与网络带宽。
  • 如果你经常只访问单个 field，hash 很合适；若经常遍历全部 field，注意切换到合适编码或拆表。

4) Set（底层：intset / hashtable）

编码

  • 小的只包含整数的集合使用 intset（紧凑数组）；
  • 否则使用 hashtable（常规集合实现）。

内部实现

  • intset：连续的有序整数数组（紧凑）；查询用二分查找或线性。
  • hashtable：普通哈希表，支持 O(1) 插入/删除/查找。

复杂度

  • SADD/SREM/SISMEMBER：O(1)（hashtable）
  • SMEMBERS：O(N)

常用命令

  • SADD, SREM, SMEMBERS, SISMEMBER, SPOP, SCARD, SINTER, SUNION, SDIFF

使用建议 / 坑

  • 集合交集/并集的时间与集合大小相关：SINTER 会把小集合优先作为筛选条件。
  • 避免在非常大的 set 上执行 SMEMBERS（会返回整表）。

5) Sorted Set（ZSet — 底层：skiplist + dict）

为什么用跳表 + 哈希表？

  • 跳表（skiplist）支持有序集合的 按 score 范围检索、按 index 排序、范围扫描，而哈希表提供从 member 到 score 的快速映射（回查）。
  • 两结构配合：跳表用于按 score 排序，dict 用于按 member 快速查找。

复杂度

  • ZADD / ZREM：O(log N)（跳表插入/删除）
  • ZRANGE by index：O(log N + M)（定位 + 扫描 M 个）
  • ZRANGEBYSCORE：O(log N + M)

内部实现

  • 跳表节点包含 member、score、forward 指针（多层），随机 level（概率性平衡）。
  • dict 映射 member → score，便于检查重复 & 更新。

常用命令

  • ZADD, ZREM, ZRANGE, ZRANGEBYSCORE, ZPOPMIN, ZINCRBY, ZCARD, ZRANK, ZREVRANGE

使用建议 / 坑

  • 排行榜、延迟队列（score=timestamp）是典型用例。
  • 特别注意：大量更新排名（频繁 ZADD 改 score）会导致跳表频繁重排，影响 CPU。
  • big ZSet 的 ZRANGE 0 -1 会返回所有元素 — 小心内存/网络。

6) Bitmap（位图）

实现原理

  • 把位域映射到字符串（String）的某些 offset（bit），底层仍然是 String（SDS），但通过位操作实现高效存储。

常用操作 & 复杂度

  • SETBIT key offset value：O(1)
  • GETBIT key offset：O(1)
  • BITCOUNT key [start end]：O(N)（按字节扫描）
  • BITOP（AND/OR/XOR/NOT）对多个 String 做按位操作

典型场景

  • 用户签到/活跃标识（每天一个 offset）
  • 大规模去重 / 标志位统计
  • 按位压缩存储大量 boolean 值

坑

  • offset 非常大时会产生稀疏大字符串（内存占用大），要评估最大 offset。

7) HyperLogLog（概率性算法用于基数估算）

原理

  • 使用概率算法估算基数（去重后的 count），核心是基于前导零计数的哈希桶。Redis 的实现基于 HyperLogLog 论文（Flajolet 等）。

特性

  • 单个 HyperLogLog 占用极小内存（大约 12KB），适合海量 UV（独立用户）统计。
  • 误差约 0.81%（典型实现）。

常用命令

  • PFADD key element [element ...]：添加
  • PFCOUNT key [key ...]：估算基数（支持合并多个 HLL）
  • PFMERGE destkey sourcekey [sourcekey ...]：合并

使用建议 / 坑

  • 不能用于确切计数；只用于需要空间换精度的大规模统计。
  • PFMERGE 是近似合并——误差依旧存在，但仍可用于聚合人群统计。

8) GEO（geohash + sorted set）

实现思想

  • Redis 用 geohash 将经纬度映射成字符串表示（geohash），并把 geohash 或距离映射到 Sorted Set 的 score（或以 geohash 作为 member 存储元信息），从而利用 ZSet 的范围检索能力实现地理范围查询与半径查找。

常用命令

  • GEOADD key longitude latitude member
  • GEORADIUS key longitude latitude radius m|km（已废弃，推荐 GEOSEARCH）
  • GEOSEARCH, GEOHASH, GEOPOS, GEODIST

复杂度

  • 基于排序与区间查找，性能与集合大小和所选择的 geohash 精度有关。

使用建议 / 坑

  • 对大范围精确计算要借助外部计算（因为 geohash 是近似网格）。
  • 使用 GEOSEARCH 新 API 更灵活高效。

9) Stream（Redis Streams — 底层：radix-tree + listpack + stream groups）

Streams 是 Redis 5.0 引入的日志流数据结构，功能类似 Kafka（但轻量嵌入式），支持持久化、消费组、ACK、PENDING、trim 等。

9.1 核心数据结构

  • Radix-tree（压缩前缀树）：用于索引 stream 的各个节点（ID -> entry），便于快速查找与范围扫描。
  • Listpack（或旧 ziplist）：紧凑数组结构，用来存储 entry 的 field/value（以节省空间）。多个 entry 被打包成块（chunk），每个 chunk 存磁盘 segment。
  • Stream entries：每条 entry 有一个自增的 ID（格式：milliseconds-sequence），和若干 field/value。

9.2 消费模型

  • Consumer Group：类似 Kafka consumer group，支持多消费者分担消费任务。
  • Pending Entries List (PEL)：每个消费组为每个分区（stream）维护的未确认消息列表，记录被分配但未 ACK 的消息（用于重试/重分配）。
  • XREADGROUP / XREAD / XACK / XCLAIM / XPENDING：常用消费组命令。
  • 自动 ID 分配：XADD key * field value 会自动生成 ID（基于时间戳+序列）。

9.3 复杂度与性能

  • 写入（XADD）：顺序追加，效率高，COW & persistence依赖 Redis 的持久化设置。
  • 读取（XREADGROUP）：可做阻塞或非阻塞，消费组会分配给活跃 consumer。
  • stream 在高吞吐场景下比 List 更具优势（支持消费组、ACK、pending），但内部 PEL 可能占内存（需管理 pending）。

9.4 常见命令 & 场景

  • XADD, XGROUP CREATE, XREADGROUP, XACK, XCLAIM, XPENDING, XRANGE, XREVRANGE, XTRIM
  • 场景：任务队列、事件溯源、轻量级消息流、CDC 缓冲

9.5 重要细节与坑

  • 消费组导致的内存：如果消费者不 ack，PEL 会增长，导致内存占用增加；需要监控并通过 XACK 或 XCLAIM 恢复。
  • ID 单调性：ID 基于时间戳，跨实例时间不一致会影响顺序；XADD 支持显式 ID。
  • trim 策略：XTRIM 用于限长，避免流无限增长。
  • 延迟重试：使用 XCLAIM 或 XPENDING 来重分配僵尸 consumer 的 pending 消息。

速记清单

  • SDS 优点：O(1) length，二进制安全，预分配
  • quicklist = ziplist chunks + linked list：头尾 O(1)，内遍历 O(N)
  • hash 小用 ziplist，大用 hashtable（阈值可配置）
  • Set 小整数用 intset，大用 hashtable
  • ZSet = skiplist + dict：skiplist for range, dict for O(1) member lookup
  • Bitmap 基于 String 的 bit 操作：适合大规模 boolean 标志
  • HLL：12KB 估算基数，误差 ≈ 0.81%
  • GEO：geohash + zset 实现经纬度查询
  • Stream：radix-tree (index) + listpack (entry store) + consumer-group（PEL）

实战建议

  1. 避免 big key（过长 list/zset/hash）——拆分或分页
  2. 关注编码切换阈值（redis.conf 中相关参数）以控制何时从 ziplist 切换到 hashtable
  3. 监控 memory fragmentation、used_memory、rss（listpack/ziplist 对内存友好，但会增加 CPU）
  4. 流（Stream）适合需要 ACK/重试的场景，但注意 PEL 管理与 trim
  5. 使用合适的数据结构：频繁按 score 范围查询用 ZSet；频繁随机访问 field 用 Hash；高并发布尔标识用 Bitmap；大规模去重用 HyperLogLog
  6. 时间序列 / 队列：考虑 Stream（消费组）优于 List（单消费者或少量消费者）
