Redis — 基础知识

一、Redis 架构体系

Redis 是一个 基于内存、单线程为主、支持持久化与网络 IO、多数据结构、多角色运行模式 的高性能数据库。

核心架构特点：

  • 单线程执行命令（事件循环 + 文件事件处理器）
  • 多线程负责：IO、多路复用、持久化 RDB/AOF 写盘、集群通信
  • 基于 Reactor 模式的文件事件驱动
  • 轻量级任务：命令解析、键值计算、事件调度
  • 重任务异步化：删除 big key、AOF 重写、持久化压缩等

关键组件：

  • Network Layer：BIO 模型，多路复用（epoll/kqueue）
  • Command Processor：RESP 协议
  • Core Engine：DS + Eviction + Expire Management
  • Persistence Layer：RDB / AOF
  • Replication / Sentinel / Cluster

Redis 的性能来自：

  • 内存操作 + 单线程避免锁开销
  • 数据结构高度优化（ziplist、hashtable、quicklist、skiplist）
  • 批处理：pipeline、事务 MULTI
  • I/O 多路复用

二、数据类型与底层结构

Redis 支持 5 大基础类型 + 3 个高级结构。

基础类型

  • String（int、raw、embstr）
  • List（quicklist）
  • Hash（ziplist/hashtable）
  • Set（hashtable）
  • Sorted Set（skiplist + hashtable）

高级数据结构

  • Bitmap
  • HyperLogLog
  • GEO（geohash + sorted set）
  • Stream（radix-tree + listpack）

三、数据结构编码优化

Redis 会根据数据规模 自动切换编码：

类型 编码方式 条件
List ziplist → quicklist 元素数/长度阈值
Hash ziplist → hashtable field/value 过大
Set intset → hashtable 不是整数 or 数量过多
ZSet ziplist → skiplist 元素过多 or score 排序复杂

面试常问：
为什么 ziplist 高效？

  • 内存连续，利用 CPU cache locality，减少碎片
  • 小数据压缩，提高空间利用率

为什么切换为 hashtable/skiplist？

  • 当数据多时，ziplist 随机访问慢（O(n)）
  • 复杂度退化，需要更快结构

四、持久化机制

Redis 提供 2 种：

RDB（快照）

  • fork 子进程 dump 快照
  • 紧凑、体积小
  • 恢复快
  • 但会丢失最近一段时间的数据

触发方式：

  • 自动（配置 save）
  • 手动 bgsave
  • 主从复制自动同步时发送 RDB

AOF（日志）

  • 追加写命令，三种策略：
    • always
    • everysec（默认）
    • no
  • 定期 AOF rewrite 重写
  • 空间较大，但数据安全

推荐组合

RDB + AOF（默认 everysec）

五、内存管理与淘汰策略

过期键删除策略

  • 惰性删除（访问时检查）
  • 定期删除（随机抽样）

重点：Redis 不会扫描全库，只随机抽样一部分 keys。

内存淘汰策略（maxmemory）

  1. noeviction（默认）
  2. allkeys-lru（推荐，高并发缓存场景）
  3. volatile-lru
  4. allkeys-lfu（最精准）
  5. volatile-lfu
  6. volatile-ttl
  7. allkeys-random/volatile-random

面试爱问：
LRU、LFU 实现？

  • LRU：Redis 采用 近似 LRU（采样算法）
  • LFU：使用计数衰减（log 型累加 + 时间衰减）

六、事务与 Lua

事务功能很弱：

  • 不支持回滚（因为命令执行在单线程）
  • MULTI/EXEC/QUEUE
  • WATCH 乐观锁（CAS）

Lua 脚本：

  • 原子执行
  • 高级事务替代方案

典型面试案例：
秒杀、扣库存、分布式锁

七、Redis 锁机制（分布式锁）

实现方案：

正确写法（SET NX PX + LUA 解锁）

解锁脚本必须检查 value

RedLock

  • 多机房部署
  • 获取过半节点锁
  • 自动漂移算法

面试观点：
RedLock 在互联网场景不推荐（时钟漂移和网络问题）
推荐：

  • 单机 Redis + AOF everysec
  • 或使用 Redisson

八、高可用（主从 + Sentinel + Cluster）

主从复制

  • psync：部分复制、位点恢复
  • 异步复制，主挂会丢数据

Sentinel（哨兵）

负责：

  • 监控
  • 通知
  • 自动故障转移

关键点：
consensus 需要 majority 多数派哨兵同意。

Redis Cluster（分片）

核心：

  • 16384 槽（slot）
  • CRC16 % 16384
  • 每个节点负责一部分 slot
  • 客户端重定向 MOVED/ASK

一致性保证：

  • 单节点强一致
  • 集群整体最终一致
  • 复制是异步，仍可能丢失数据

九、Redis 性能优化

常见瓶颈

  1. big key（阻塞风险）
  2. 大量 keys 扫描（不要用 KEYS，用 SCAN）
  3. AOF fsync 阻塞
  4. 网络延迟
  5. CPU 单线程瓶颈

性能提升手段

  • pipeline 批处理
  • io-threads 开启（仅网络 IO）
  • 延迟删除 big key（UNLINK）
  • 持久化开 async I/O
  • 使用专业缓存结构（hash 代替 string）

十、典型问题与解决方案

缓存穿透

  • 布隆过滤器
  • 缓存 null 值

缓存击穿

  • 热点 key 加互斥锁
  • 或逻辑过期 + 后台刷新

缓存雪崩

  • key 过期时间随机
  • 多层缓存（本地+远程）
  • 开启集群分散压力

十一、集群原理与一致性细节

Cluster 关键点：

  • gossip 协议
  • slot 迁移
  • failover 分析
  • 主从切换
  • 频繁重定向

面试重点问：
ASK 与 MOVED 区别

  • MOVED：客户端更新路由表
  • ASK：重定向一次，不更新路由

十二、Redis 多线程与 IO 模型

Redis 6 后新增多线程，只处理：

  • 网络读写
  • 数据解析

核心命令执行依然单线程。

IO 模型：
Reactor + epoll
