Redis的高性能

一、Redis 为什么单线程却这么快？

Redis 的高性能并不是因为“单线程快”，而是因为：

1. 所有操作都在内存中完成（In-Memory）

  • 无磁盘随机 I/O
  • 内存访问延迟只有 100ns 级别
  • 远比磁盘快 数万倍

内存速度本身就快到爆。

2. 单线程模型避免了线程切换开销

其他数据库（如 MySQL）使用多线程，每次处理都要：

  • 上下文切换
  • 线程竞争资源
  • CPU 缓存失效

这些都是昂贵的操作。

Redis 单线程 = 没有锁竞争 + 没有上下文切换。

👉 减少系统开销 = 真正的性能提升来源。

3. 使用 I/O 多路复用（epoll）处理大量连接

Redis 并不是一个线程处理一个连接。

它采用 Reactor 模型 + epoll/select/kqueue：

  • 内核监听所有 socket 事件
  • 当某个 socket 可读时，触发事件
  • Redis 注册的回调函数被唤醒，执行读 → 处理 → 写

多连接不等于多线程，Redis 单线程就能处理成千上万的连接。

4. 高效的数据结构

Redis 对数据结构做了极致优化：

结构 优化点
dict 渐进式 rehash，O(1) 查询
skiplist 有序集合专用，插入/查找 O(logN)
ziplist / listpack 小数据紧凑存储，减少内存碎片
SDS 字符串 预分配、二进制安全、避免频繁扩容

这些都是为了“快”。

5. CPU Cache Friendly（缓存友好）

Redis 的代码 + 数据结构布局尽量保证：

  • 连续内存访问
  • 少指针跳转
  • 减少 CPU cache miss

CPU 缓存命中率对性能影响比算法复杂度更大。

Redis 在这方面做到极致。

二、那多个请求同时来时，Redis 怎么处理？

Redis 是单线程处理命令，但不是“一次只处理一个请求”。

处理流程如下：

1. 每个客户端连接对应一个 socket

客户端可能一万、十万、几十万。

2. epoll 监听所有连接，只唤醒有事件的 socket

Linux 内核负责：

  • 有数据可读 → 唤醒 Redis
  • 有连接进来 → 唤醒 Redis
  • socket 可写 → 唤醒 Redis

Redis 不需要轮询所有连接，只处理有事件的连接。

这就是 I/O 多路复用的力量。

3. Redis 主线程依次处理事件（事件循环）

事件循环大致为：

单线程，但非常快。

4. 每个命令执行极快（微秒级）

比如：

  • GET：0.1~0.5 µs
  • SET：0.5~1 µs

假设一个命令 1 微秒，1 秒能处理约 100 万个请求。

所以虽然命令是串行执行，但：

  • 每个命令快
  • 串行也能处理巨大吞吐量

Redis QPS 达到 10万–50万 是常态。

5. 避免请求被堵塞的机制

为了防止耗时操作阻塞主线程：

Redis 把耗时任务分给后台线程：

  • 异步删除（unlink）
  • RDB/AOF 持久化
  • AOF rewrite
  • 大 key 删除
  • 集群数据迁移

这些都是“后台线程池”处理，而不是主线程。

三、扩展问题

Q1：Redis 单线程会不会因为慢操作阻塞？

会，但可通过：

  • 避免 big key
  • 使用 unlink 异步删除
  • 使用 pipeline
  • 控制复杂度高的命令（如 KEYS、SMEMBERS 全量扫描）
  • 使用 布隆过滤器 / 分片结构

Q2：Redis 为什么不改成多线程？

其实 Redis 6 已经在：

  • I/O 读写 → 多线程
  • 命令执行 → 仍然单线程（保证原子性）

Redis 作者一句话说明本质：

“多线程不一定更快，反而会出问题；**Redis 的瓶颈不是 CPU，而是网络.**”

Q3：多个请求并发会不会互相覆盖？

不会。

因为 Redis 单线程处理命令 → 自然保证命令原子性。

不需要加锁。
